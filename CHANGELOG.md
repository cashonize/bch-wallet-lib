# Changelog

## Unreleased

Starting point: mainnet-js `4.0.0-next.14` (`next` @ `9ec2a0e`), plus mainnet-js#244 (128-byte NFT commitments).

### Changes for callers coming from mainnet-js

- Package name `bch-wallet-lib`; `@mainnet-cash/indexeddb-storage` is now the `bch-wallet-lib/indexeddb` subpath export.
- The CLI (`src/cli.ts`) and the browser bundle are not shipped.
- The Electrum transport is `@electrum-cash/network` with `@electrum-cash/web-socket` instead of `@rpckit/*`:
  - Servers are plain URLs, `wss://host:port` or `ws://host:port`. `createProvider(network, servers?, options?)` and `DefaultProvider.servers.<network>` take one URL, several separated by commas, or an array (`getDefaultServers` now returns an array). A list is tried in order when connecting, and the provider stays with the first server that connects: after a failure electrum-cash reconnects to that server and restores its subscriptions there. rpckit's notation (`fallback(...)`, `?timeout=…&batchSize=…` options) is rejected with an Error, and requests are no longer batched.
  - `new ElectrumNetworkProvider(transport, network)` takes a `Transport`, the new interface of what the provider needs (`connect`, `close`, `request`, `subscribe`), e.g. `new ElectrumTransport("wss://host:50004")`. The class is no longer generic over an rpckit schema, and `performRequest<T>(method, params)` / `subscribeRequest(method, params, callback)` take the result type from the caller instead of the schema.
  - Every server gets a connect timeout (10 s) and a request timeout (30 s), a single user-supplied URL included (mainnet-js#251); `ElectrumTransportOptions` (`connectTimeout`, `requestTimeout`, in ms) is the third argument of `createProvider`. A timed out request rejects with an `ElectrumTimeoutError`, no longer with the string `"electrum-cash request timed out, retrying"`. Errors are always `Error` objects.
    - Retry: a request that times out or loses its connection is sent once more, on a (re)connected server, where it used to be awaited again on the same one. If the first send's answer still arrives before the second's, it is taken. A broadcast is never sent again, nor is a request the server answered with an error.
    - Dead connections: a connection that stays silent after a send for half the request timeout, or for the connect timeout if that is shorter (10 s with the defaults), is taken for dead and replaced, so that a re-sent request goes to a fresh connection rather than the dying one, e.g. after iOS / Safari dropped the socket of a backgrounded page.
    - Caps: for a server given by URL that same shorter value is the socket's own timeout, which also bounds opening the socket, so a `connectTimeout` above half the `requestTimeout` does not give a server longer to connect (`connectTimeout: 20_000` with the default request timeout still gives up after 15 s), and a `requestTimeout` above twice the `connectTimeout` does not make a silent connection last longer. A server passed as an electrum-cash socket keeps the timeout it was set up with; `connectTimeout` still bounds its connect.
  - In a browser the socket stays connected while the page is hidden and ignores online/offline events; it reconnects when the connection actually fails. In Node, TLS certificates are verified.
  - Protocol version 1.5 is asked of every server (mainnet asked for 1.6), as electrum-cash only accepts the exact version it asks for and chipnet servers stop at 1.5.
  - `daemonPassthrough()` is removed: Fulcrum's `daemon.passthrough` takes named params, which electrum-cash cannot send. The regtest `mine()` calls the node's RPC directly, with the `RPC_*` environment of the regtest (as mainnet-js 3 did).
  - New exports: `ElectrumTransport`, `ElectrumTimeoutError`, and the types `ElectrumServer`, `ElectrumTransportOptions`, `Transport`, `Unsubscribe`.
- `initProviders` / `disconnectProviders` no longer throw a `ReferenceError` in a browser that has no global `process` (mainnet-js#251).
- `createMockProvider` and `MockNetworkProvider` are now exported from the new `bch-wallet-lib/mock` subpath, which needs `@paryonusd/mem-cash` installed; the main entry no longer imports them, not even dynamically, so bundlers no longer fail on the mock chain's imports (mainnet-js#251). `initProvider` / `initProviders` / `disconnectProviders` no longer read `USE_MOCK_PROVIDER`: call `initMockProvider()` from `bch-wallet-lib/mock` to install a mock chain as the regtest provider.
- The HD wallet cache keeps its record in mainnet-js 3.1.7's form again: entries keyed `${walletId}-${index}-${change}`, each with its `index` and `change`, and an `indexCache` from address to `{ index, change }`. next.14 had rekeyed it to `${walletId}-${path}` with a `pathCache`, so it ignored the cache of every wallet 3.1.7 had opened (and dropped those entries on load, rewriting the record), and 3.1.7 ignored its cache after a rollback. A wallet opened on what 3.1.7 wrote now reuses those addresses, statuses, utxos and history and writes nothing on load, and 3.1.7 reuses what the library writes. Only branches 0 and 1 of a wallet built on an account node have a place in that form: addresses on other branches, and those of a depth-4 (single-chain) wallet, are cached in memory only. Entries in next.14's form are not read, and are dropped at the next write (mainnet-js#251).
- `GAP_SIZE`, `DEFAULT_BRANCHES`, `DEPOSIT_BRANCH`, `CHANGE_BRANCH` and the `HDWalletOptions` type are exported from the entry again, as in mainnet-js 3 (mainnet-js#251).
- `sendMax`, `send` and the token operations no longer write to the caller's options object (`sendMax` set `options.utxoIds`, a token send appended to `options.ensureUtxos`), nor does `waitForTransaction` (`getTransactionInfo`), so reusing an options object, e.g. for a retry, no longer carries the previous inputs forward (mainnet-js#251).
- New export `InsufficientFundsError`, thrown wherever the wallet's coins (or the given `utxoIds`) cannot cover a send, a genesis, a mint or a burn, with `asset` (`"bch"` or `"token"`) and, for a token, its `category`; tell it apart with `instanceof` instead of matching messages. The messages are unchanged: "Amount required was not met…", "There were no Unspent Outputs", "The available inputs couldn't satisfy the request with fees", "The available inputs in the wallet cannot satisfy this send request", "Insufficient funds for transaction given fee", "Not enough vout=0 inputs available for new token genesis…", "Not enough token amount to send", "No suitable token utxos available to send token…", "You do not have any token UTXOs with minting capability…", "You do not have suitable token UTXOs to perform burn…" (mainnet-js#251).
- New `wallet.setProvider(provider)` switches an existing wallet to another electrum provider of its network: the wallet's subscriptions (status watches, an HD wallet's address discovery, `watchBlocks`, and pending `waitForTransaction` / `watchDoubleSpends` subscriptions) are made again on the new provider and ended on the old one, which is left connected (mainnet-js#251). If the new provider cannot connect, or a subscription cannot be made there, `setProvider` rejects and the wallet stays on the old provider with its subscriptions; a retry with the same provider tries again. If the old provider also fails while the subscriptions that did move are moved back, those stay on the new provider until the next `setProvider` call moves them, so call it again. Moved status watches get the new server's current status, as when they start, so a `watchBalance` / `watchTokenBalance` callback may fire with an unchanged value (an HD wallet's status watches fire once per watched address); a moved `watchBlocks` callback gets the new server's tip only if it differs from the last header it saw. `wallet.provider` is now a getter: assigning it (the old workaround, under a `@ts-ignore`) throws a `TypeError`, so call `await wallet.setProvider(provider)` instead. `waitForBlock` still waits on the provider it started on.
- `wallet.stop()` now also ends `watchBlocks` subscriptions and pending `waitForTransaction({ txHash })` / `watchDoubleSpends` subscriptions, which it left running before, and a subscription still being made when `stop()` runs (e.g. a `watchBlocks` called just before it) is ended once it is made, where it stayed live before. The protected `cancelFns` / `trackCancelFn` are replaced by the protected `subscribe(fn)`.
- An HD wallet's `stop()` now makes the cache write it had scheduled (they are debounced by 2 s) before it resolves, where the write came up to 2 s after `stop()`; a write that fails does not make `stop()` reject.
- `waitForTransaction({ txHash })` for a transaction the server already knows now ends its subscription; it left it running, and with `setProvider` it would have followed the wallet to each new provider.
- A subscription that cannot be made (e.g. the server is unreachable) no longer leaves what waits on it pending forever (part of mainnet-js#256): `waitForTransaction({ txHash })`, `waitForBlock` and `sendRawTransaction(hex, true)`, which make a subscription of their own, reject with the error. `waitForBalance`, `waitForTokenBalance` and `waitForTransaction` without a `txHash` wait on the wallet's status watch, and reject with its error as the wallet's reads do (next entries).
- An HD wallet's address discovery now settles when an address's subscription or its first fetch fails (mainnet-js#256); it hung before, with an unhandled rejection. `getUtxos`, `getBalance`, `getRawHistory` and `watchStatus` reject with that error, and the next of them runs discovery again first, subscribing the addresses that failed, so a wallet constructed offline recovers once a read succeeds and no longer needs rebuilding. `scanMoreAddresses` rejects with the error, and a later scan retries what it missed; reads only retry the default gap, and the gap maintenance subscribes the missed addresses once used addresses bring them inside it. After `stop()` reads no longer retry, they reject with the last error. A fetch that fails after discovery, on a later status notification, leaves that address's state as it was until its next notification fetches again, without an unhandled rejection. `watchPromise` still never rejects. `watchBalance`, `watchTokenBalance`, `watchTransactionHashes` and `watchTransactions` skip a notification whose read fails (e.g. while a gap extension has failed), and report the error as below, instead of producing an unhandled rejection.
- A single-address or watch-only wallet whose status subscription or first fetch fails now does what an HD wallet's discovery does (mainnet-js#256): `getUtxos`, `getBalance`, `getRawHistory`, `getHistory` and `watchStatus` reject with the error, and the next of them subscribes again, so a wallet constructed offline recovers once a read succeeds. Before, a failed subscription let them go on with the cached (or empty) state, and a failed first fetch did the same without any error. After `stop()` reads no longer retry; they reject with the last error. A fetch that fails on a later notification leaves the wallet's state and status as they were, so the next notification fetches again; the status of the failed fetch used to be taken as current, which kept the stale state until the address changed again. Status watchers are now called once the notification's fetch is done instead of before it. `watchPromise` still never rejects. Callers that read right after constructing a wallet must handle the rejection; calling the read again retries.
- Watch callbacks may be async, and their errors are reported the same way on every wallet type: a callback's throw or rejected promise, and a read the watch makes for it that fails (the balance read of `watchBalance` / `watchTokenBalance`, the history and transaction reads of `watchTransactionHashes` / `watchTransactions` / `watchTokenTransactions`, the dsproof subscription of `watchDoubleSpends`), goes to the watch's new `onError` option, or to `console.error` without one, and the watch goes on. Before, it was dropped silently (an HD wallet's watchers, a single-address wallet's throwing callback) or became an unhandled rejection, which ends a Node process by default (a single-address wallet's async callback, `watchBlocks`, the provider's subscriptions). The option is the new last parameter, a `WatchOptions` (new export): `watchStatus(cb, { onError })`, `watchBalance(cb, { onError })`, `watchTokenBalance(category, cb, { onError })`, `watchTransactionHashes` / `watchTransactions` / `watchTokenTransactions(cb, { onError })`, `watchBlocks(cb, skipCurrentHeight, { onError })` and `watchDoubleSpends(cb, window, { onError })`; an HD wallet's `watchStatus(cb, debounce)` takes `{ debounce, onError }` and still accepts the number. A callback passed to the provider's `subscribeToAddress`, `subscribeToTransaction`, `subscribeToDsproof`, `subscribeToHeaders`, `subscribeRequest`, `watchAddressStatus` or `watchBlocks` gets `console.error`. The new transactions of one notification are reported each on its own, so one that fails no longer keeps the next from being reported. Callback types return `unknown` instead of `void`, so an async callback type-checks under `no-misused-promises`; wrappers that only exist to turn an async callback into a void one can go.
- `waitForBalance`, `waitForTokenBalance` and `waitForTransaction()` (without a `txHash`) reject when a read made for their watch fails, e.g. an HD wallet's balance read while a gap extension has failed, and end their watch; they waited forever, with the error dropped or unhandled. `sendRawTransaction(hex, true)` for a transaction the server already knows now ends its subscription, which it left running.
- A watch-only or single-address wallet's `waitForUpdate` starts its timeout once its status watch is in place, as the HD wallet's does; it threw a `TypeError` when the wallet's first subscription took longer than the timeout.
- A wallet cache write that fails (e.g. storage full) and an exchange rate that cannot be cached no longer surface as unhandled promise rejections, which end a Node process by default; the cache write is redone by the next one, and the rate is still returned.
- The fee rate is no longer read from or cached in the globals `BCH_RELAY_FEE` / `tBCH_RELAY_FEE` / `rBCH_RELAY_FEE` (BCH per kB): set the new `Config.RelayFeePerByte` (satoshis per byte) instead, e.g. `Config.RelayFeePerByte = 1` for `globalThis.BCH_RELAY_FEE = 0.00001`; it applies to every network. Without it, the server's `blockchain.relayfee` is cached per provider rather than process-wide, so a wallet moved to another server with `setProvider` uses that server's rate (mainnet-js#254).
- The server's `blockchain.relayfee` is checked against the new `Config.MaxRelayFeePerByte` (default 10 sat/byte): a server rate above it is taken as untrusted and ignored, and sends pay 1 sat/byte (the network's relay minimum), with a console warning. It was used unchecked, so a server could make every send pay any fee it chose; clamping it to the cap instead would still let a hostile server make every send pay 10 times the minimum. A caller that trusts its server's higher rate raises the cap, and one that wants a higher rate sets `Config.RelayFeePerByte`. The fee rate is never below 1 sat/byte, the network's relay minimum, whatever the server reports or the settings say (a missing, non-finite or lower server rate gives 1 sat/byte; so does a `Config.RelayFeePerByte` below 1, which was used as given and built transactions that do not propagate). `Config.RelayFeePerByte`, when set, is not bounded by the cap. Both settings must be finite, non-negative numbers: anything else (`NaN`, a negative number, `Infinity`, a string) makes every send reject with an `Error` naming the setting, before anything is built (mainnet-js#254).
- `watchTransactionHashes`, `watchTransactions`, `watchTokenTransactions` and `watchDoubleSpends` report only transactions that are new after the watch started, each once, for single-address and HD wallets alike (mainnet-js#257). They replayed the whole history as new when the first new transaction arrived, mixed in with it (and `watchDoubleSpends` subscribed to a dsproof for every replayed one). A caller that pre-seeded a dedupe set from `getRawHistory()` can drop it; one that relied on the replay reads `getRawHistory()` before watching. The set of known transactions is taken when the watch is set up, so start it before the send it should see.
- An NFT input or output given without a `commitment` (only possible from untyped code) now gets empty commitment bytes in the libauth transaction instead of `false`; the encoded transaction is unchanged. `ElectrumNetworkProvider.ready()` is typed `Promise<void>` and `NetworkProvider.ready()` `Promise<unknown>`, the types that `Promise<boolean | unknown>` already amounted to.
- The first exchange rate fetched outside the browser cache (in Node, or in a browser whose localStorage throws) is now cached for the TTL like later ones; it was not stored, so the next conversion fetched again and the `getExchangeRatePromise()` warm-up warmed nothing (mainnet-js#262).
- Cached exchange rates follow `Config.GetExchangeRateFn`: once it is set to another function, the rates cached from the previous one are no longer served, nor is a rate that was still being fetched from it when it changed; the first conversion after the switch fetches from the new source. Assigning a new function is all a caller does, nothing needs clearing. A change is noticed by the next rate lookup, so switching away and back before any lookup keeps the cache. Until the first change in a process, rates cached by an earlier run (mainnet-js 3's included, whose `rate-<symbol>` entries keep their key and shape, now with a `source` field added) are still used. In a browser, a rate fetch that fails no longer fetches a second time through the in-memory cache; the error is thrown directly.
- New `ExchangeRate.getQuote(symbol, { useCache?, staleOnError? })` returns `{ symbol, rate, fetchedAt, stale }` (`fetchedAt` in ms since the epoch), with the new types `ExchangeRateQuote` and `ExchangeRateOptions`. With `staleOnError: true`, a fetch that fails returns the last cached rate of the current source for that symbol, however old, as `stale: true`, instead of throwing; check `fetchedAt` to decide whether it is still good enough. Without a cached rate it throws the fetch's error. Without the option, and in `ExchangeRate.get` and the conversion helpers, a failed fetch throws as before. A rate fetched with `useCache: false` is not cached, so it does not become a later fallback.
- `getHistory` no longer throws on an output or a spent input whose locking bytecode has no CashAddress (P2S, P2PK, bare multisig); its `address` is `SCRIPT: <hex>`, as an OP_RETURN output's is `OP_RETURN: <hex>` (mainnet-js#252). Every input and output now carries its `lockingBytecode` (hex), and every input its spent `outpointTransactionHash` and `outpointIndex` (mainnet-js#248); a coinbase input has none of these.
- `decodeTransaction` no longer throws on an output without a CashAddress: an OP_RETURN output's `scriptPubKey.addresses` is `["OP_RETURN: <hex>"]` and a P2S or bare multisig output's `["SCRIPT: <hex>"]`, as in `getHistory`, with the locking bytecode in `scriptPubKey.hex` as before (a P2PK output keeps the P2PKH address of its key). Token outputs now carry `tokenData` in the server's verbose format (`amount` as a decimal string, hex `category`, `nft.capability` and hex `nft.commitment`); it was dropped. A new last parameter `{ provider }` (`DecodeTransactionOptions`) fetches the transaction and, with `loadInputValues`, its inputs from that provider, whose network then decides the address prefix (passing a different `network` as well throws); without it the network's global provider is used as before, now only when something has to be fetched. New `wallet.decodeTransaction(hashOrHex, loadInputValues?)` decodes on the wallet's own provider and network: use it instead of the standalone function, which fetched from the global provider whatever provider the wallet was on.
- `SignedMessage.verify` matches the address by its decoded payload and type instead of by string: an uppercase or prefix-less cashaddr of the signing key now verifies (a given prefix still has to be the address's own, which its checksum checks), and only a P2PKH address (with or without token support) can match; a P2SH address with the key's hash as its payload matched before. It no longer throws on a signature that is not base64, has a recovery byte outside 31..34 or recovers no key, nor on an address that does not decode: it returns `valid: false` (with `signatureValid: false`, or `publicKeyHashMatch: false` for the address). The result shape is unchanged; callers that lowercased the address or caught throws can drop that.
- `OpReturnData.fromArray` / `from` / `fromString` / `fromUint8Array` build OP_RETURN scripts up to the standard 223 bytes (the whole script, the `OP_RETURN` and push opcodes included); they refused more than 220, so standard outputs of 221 to 223 bytes threw. Pushes of 76 to 255 bytes use `OP_PUSHDATA1`; the error is now "OP_RETURN script can not exceed 223 bytes in size". A send whose OP_RETURN outputs add up to more than 223 bytes, the limit BCHN applies to the sum over a transaction, now throws "OP_RETURN outputs can not exceed 223 bytes in total, got N" before anything is broadcast, instead of being refused by the node as `oversize-op-return`. The limit is exported as `MAX_OP_RETURN_BYTES` (mainnet-js#260).
- `OpReturnData.parseBinary` (and `OpReturnData.parse`) reads every push of the script: it stopped at the first empty push (`OP_0`), dropping every later chunk, and read `OP_1NEGATE` and `OP_1`..`OP_16` as pushes of 79 and 81 to 96 bytes. An empty push now gives an empty chunk, `OP_1NEGATE` the byte `0x81` and `OP_1`..`OP_16` the bytes `0x01`..`0x10`. It now throws on what it misread silently before: a script that does not start with `OP_RETURN`, a non-push opcode, or a push longer than the bytes left; callers reading untrusted outputs should catch that (mainnet-js#260).
- A send with both `buildUnsigned: true` and `broadcast: false` now returns the unsigned transaction as `unsignedTransaction`, with `sourceOutputs`, as `buildUnsigned: true` alone does; it returned it as `transaction` with a `txId` of the unsigned transaction, which no signed transaction would have.
- `send`, `sendMax`, `tokenGenesis`, `tokenMint` and `tokenBurn` now also return the transaction they broadcast, as hex in `transaction`, as a `broadcast: false` send already did (mainnet-js#245). Their result is typed by the `buildUnsigned` option: without it (or with `false`) a `SignedSendResponse`, whose `txId`, `transaction` and `categories` are strings, so `response.txId!` needs no assertion; with `buildUnsigned: true` an `UnsignedSendResponse`, with `unsignedTransaction` and `sourceOutputs` set and no `txId`. When the option's value is not known to the compiler (e.g. an options variable typed `SendRequestOptionsI`) the result is the union of the two, which `txId !== undefined` narrows. `SendResponse` keeps its fields, and the new types and `SendResponseFor<B>` are exported.
- `fromWIF` and `fromId("wif:…")` errors no longer contain the WIF (mainnet-js#258). The WIF is now decoded and checked by its version byte instead of its first character: a WIF of the other network fails with "WIF is for testnet, expected mainnet" (or the reverse), replacing "Mainnet type wif … passed, should start with L or K"; a malformed one with "Invalid WIF: …". Uncompressed WIFs (mainnet `5…`, testnet `9…`) are rejected with "Uncompressed WIF private keys are not supported" on every network: the wallet only derives and signs for the compressed public key's address, which does not hold an uncompressed key's funds, and regtest wallets used to accept them onto that wrong address. Regtest wallets still accept compressed WIFs of either version byte.
- `fromId`, `named`/`replaceNamed` (with a stored or given walletId) and `walletFromId` no longer quote a walletId part they cannot place, which for an id missing its network part (`wif:<key>`, `seed:<words>`) or with no colons at all (a bare WIF) was the key itself: such an id now fails with "Unknown network prefix to a mainnet wallet", and `walletFromId` with "Unknown wallet type in walletId" / "Unknown network in walletId" instead of a `TypeError` naming the part. "Network prefix regtest to a testnet wallet" is unchanged for a known network. A watch-only wallet's `fromId` checks the network part before the wallet type.
- `getTokenChangeAddress()` now works on every wallet: it threw on all of them, as only `BaseWallet` had it and `HDWallet` implemented the method as `getChangeTokenAddress()` (mainnet-js#259). Single-address and watch-only wallets return their `tokenaddr`, an HD wallet the token form of its next unused change address. `HDWallet.getChangeTokenAddress()` stays as a deprecated alias.
- `tokenMint` and `tokenBurn` honor `options.utxoIds` as `send`, `sendMax` and `tokenGenesis` do: the minting NFT and the tokens to burn are taken from the given utxos only, and an id not in the wallet throws "Utxos [...] not found in wallet" (mainnet-js#250). Before, they picked their token inputs from all of the wallet's utxos and pinned them to the transaction, so a coin outside `utxoIds` could be spent; a mint or burn with no suitable token among the given utxos now throws `InsufficientFundsError`.
- `tokenMint` re-creates the minting NFT at the wallet's token change address (`getTokenChangeAddress()`), as `tokenBurn` does with its remainder, instead of at the address it was spent from (mainnet-js#259). An HD wallet's minting NFT therefore moves to a fresh change address with every mint rather than staying on one address; single-address wallets are unaffected.
- In an HD wallet, the NFTs minted by one `tokenMint` call and the tokens created by one multi-request `tokenGenesis` that are given no `cashaddr` each go to their own unused token deposit address instead of all to the same one (mainnet-js#259). They take the next unused addresses in the order of the outputs: for `tokenGenesis` the order of its requests, for `tokenMint` its requests grouped by category, the categories in the order they first appear and each category's requests in their order. A single default output still goes to `getTokenDepositAddress()`; single-address wallets are unaffected.
- A token `send` now builds its token change from the token inputs it spends minus the requested token outputs, per category and per NFT (mainnet-js#247). Every spent NFT no request sends comes back at the token change address with its own satoshi value and, as far as the category's fungible change covers it, its own fungible amount; the rest of the fungible change goes to one fungible-only output (with the first request of the category's `value`, 1000 sats if it has none), after the NFT ones. Before, the change copied the NFT of the first request of the category: a fungible send burned the NFT of a hybrid coin it spent (e.g. a minting NFT that also held fungible tokens), sending a minting NFT left a copy of it on the fungible change, sending a mutable NFT with a new commitment built a transaction the network rejects, and an immutable NFT could not be sent at all ("No suitable token utxos available…") while the wallet held fungible tokens of its category. A token coin passed in `ensureUtxos` whose category the send does not name now comes back as change too, where it was burned; `checkTokenQuantities: false` still builds no token change. Token change a caller builds itself, as a workaround, still works (the library then finds nothing left over) and can be dropped.
- A fungible token `send` now spends only the coins of the category its amount needs, instead of every coin of the category holding fungible tokens (mainnet-js#246), which linked every address of an HD wallet that ever received the token and grew the transaction with the holding. The fungible tokens on the coins the send spends anyway (`ensureUtxos` and the inputs of its NFT requests) count first; the rest is taken from fungible-only coins, largest first, and only when those fall short from NFT coins holding fungible tokens, largest first, whose NFT comes back as change. The token change is computed from exactly the spent coins, so nothing is burned implicitly; a send whose selection would spend a token coin the change does not account for throws instead of building the transaction. A send of NFTs alone no longer spends the fungible coins of their category, and the change outputs of a send over several categories now come in the order of the coins spent (the NFT requests' inputs first). A caller that relied on a send consolidating its token coins can send the holding to itself, or pass the coins in `ensureUtxos`. The satoshis of the token coins a send no longer spends no longer pay for it either, so a wallet holding only token coins needs plain BCH coins for the fee and the token change: sending 5 of the tokens of one of three 1000-sat coins pinned all three and paid from their 3000 sats, and now throws `InsufficientFundsError` ("Amount required was not met…", `asset: "bch"`). The shortfall checks also run in another order: a fungible token send from a wallet with no coins (or none among `utxoIds`) throws "There were no Unspent Outputs" (`asset: "bch"`) instead of "Not enough token amount to send" (`asset: "token"`), and a send that is short of both an NFT and fungible tokens reports the NFT ("No suitable token utxos available…") instead of the fungible amount.
- The fee that a send's coin selection has to cover is now estimated from the coins it selects instead of from every coin it could spend (mainnet-js#253): the selection is run again for the fee of the coins it picked until they cover their own fee, the exact fee of the built transaction included. Sizing every coin as an input made `tokenGenesis`, `tokenMint`, `tokenBurn` and token `send`s fail with "Amount required was not met" in wallets holding many token coins and little BCH (each token coin the operation does not spend asked for about 190 sats at 1 sat/byte), and made plain sends spend more coins than they need (sending 4500 sats from 100 coins of 1000 sats took 20 inputs instead of 6). When the coins fall short, the amount in that error, and in its `required`, is now the outputs plus the fee of spending every coin the send could use (the pinned coins and the BCH coins of the wallet, or of `utxoIds`), no longer counting the token coins it would not spend; or the amount its last selection asked for, if that is more. A `coinSelection` callback can be called more than once per send, with a growing `amountRequired`, and should pick for the amount it is given, as the built-in strategies do; the `inputOrdering` and `fee` callbacks can also run more than once per send, once for each selection whose fee is checked, so they should not count or log calls as sends. A `fee` strategy that asks more than the relay rate (e.g. `feeFixedPerByte(2)` or `feeAbsolute`) is now funded by the selection: the selection is redone until its coins cover the strategy's fee. Before, the coins were selected for the relay-rate estimate alone, and a transaction whose strategy asked more than they left paid less than it asked (`feeAbsolute(4000n)` sending 3000 sats from coins of 1000 built five inputs paying 2000). A `coinSelection` that never settles on coins covering their own fee now throws `Error("The fee estimate did not settle on a set of inputs")`, not an `InsufficientFundsError`, after one round per candidate coin. When the selected coins would leave a change at or below dust, which is not built and goes to the miners, the selection is redone for a change above dust, and that selection is used if it pays the miners less (a 9000 sat send from 20 coins of 1000 sats now spends 12 coins and gets 1229 sats of change back, where 11 coins would have paid 2000 sats for a 1595 byte transaction). `getMaxAmountToSend` already sized only the coins it counts and is unchanged, and `sendMax` still spends every one of those coins, also those worth less than their own input fee (possible above about 3.7 sat/byte), which the new selection would have left unspent.
- A send with `feePaidBy` other than `change` no longer charges the fee twice. The change was computed as the inputs minus the outputs minus the fee while `allocateFee` also took the fee out of the paying outputs, and the `changeThen…` modes compared the fee with the change after the fee: with `FeePaidByEnum.first`, 5000 sats sent from six coins of 1000 paid 1925 sats where its size asks for 925, and with `changeThenAny` an output paid part of a fee that the change already covered. The fee now comes out of the change before the fee, or out of the outputs for what the change does not cover, and the change is what is left after both.
- With `Config.UseLocalStorageCache`, cache entries are stored under keys prefixed `bch-wallet-lib:`, and `provider.cache.clear()` removes only those; it cleared the whole localStorage of the origin, the host app's own data included (mainnet-js#261). Entries written by mainnet-js under the bare keys (`txraw-…`, `tx-…`, `header-…`, `walletCache-…`) are no longer read nor cleared; remove them yourself if they matter, as `walletCache-…` entries hold private keys.
- A write to the localStorage cache that fails, because the storage is full (about 5 MB per origin) or blocked, is now dropped instead of failing the request whose result was being cached (`getRawTransaction`, `getHeader` and the like rejected although the server had answered) (mainnet-js#261). The `getHistory` docs now point browsers at `Config.UseIndexedDBCache`.
- `getNamedWalletId(name, dbName?)` is exported from the entry again, as in mainnet-js 3, and now does what its type says (mainnet-js#261): a name with no record returns `undefined` instead of throwing "No record was found…", and without `dbName` it reads the mainnet database (`"bitcoincash"`), where `named()` stores mainnet wallets, instead of handing the storage provider `undefined` (which `IndexedDBProvider` turned into a `"wallet"` database). It still throws when no `StorageProvider` is configured.
- New exports `purgeWalletCache(walletId)` and `pruneWalletCaches(keepWalletIds)` remove wallet cache records, which hold an HD wallet's derived private keys along with status, utxos and history, from the cache storage `Config` selects (part of mainnet-js#249). `purgeWalletCache` takes a wallet's stored id (`toDbString()`, a database row's `wallet`) and removes that wallet's record; `pruneWalletCaches` removes the record of every wallet but the given ones, e.g. records left by wallets deleted earlier. Both work out the record from the stored id without constructing a wallet, so no provider is created. Once `purgeWalletCache` resolves, no wallet of that id made before it, running or stopped, writes the record again: it keeps its cache in memory only from then on (a wallet made later, e.g. the same seed imported again, caches as usual).
- New export `deleteNamedWallet(name, dbName?)` deletes a named wallet's row and purges its cache record, so its private keys do not outlive it (mainnet-js#249); `StorageProvider.deleteWallet` still removes only the row. Like `getNamedWalletId`, it reads the mainnet database (`"bitcoincash"`) without `dbName`, and works through whatever `BaseWallet.StorageProvider` is, so an `EncryptedStorageProvider` row is decrypted to find the record. It removes the cache record before the row, and works out the record before removing either: a row whose wallet id cannot be read (e.g. a `named:` alias), or a record that cannot be removed, makes it throw with the row kept, so it can be retried. A loaded wallet need not be stopped first: it no longer writes the record, as with `purgeWalletCache`.
- New export `InvalidRequestError`, with the request `field` (`category`, `nft.commitment`, `amount` or `nft`) and the `value` given, thrown by the `TokenSendRequest`, `TokenGenesisRequest`, `TokenMintRequest` and `TokenBurnRequest` constructors, and by `send`, `tokenGenesis`, `tokenMint` and `tokenBurn` for plain request objects before they read a coin, when the token data cannot go on chain as given. A category must be 64 hex characters (`tokenMint` and `tokenBurn` threw a plain "Invalid category supplied…" `Error` for a wrong length, `send` read any string); a commitment must be an even number of hex characters and at most 128 bytes, where libauth's `hexToBin` read `"abc"` as `ab0c` and `"test"` as other bytes, so a typo built a different commitment than asked; a fungible amount must be an integer from 0 to 2^63-1 (bigint, number or digit string; a negative burn amount counted as 0 before); and a token send or genesis output needs a positive amount or an NFT, as does every mint request: such an output was built as a plain BCH output to the token address, its token data dropped. Callers that passed a text commitment convert it to hex first (e.g. `binToHex(utf8ToBin(text))`). A `tokenBurn` that leaves no fungible tokens of the category still sends the satoshis of the burned coins to the burn's `cashaddr` as a plain output, as it did. `tokenMint`'s docs now say that every request creates one output and that the library caps neither the number of requests nor the outputs.
- `ElectrumNetworkProvider.getRawTransactions` and `getHeaders` keep at most 10 requests in flight for their cache misses, instead of sending them all at once; the new last parameter `{ concurrency }` (type `ConcurrencyOptions`, also on the `NetworkProvider` interface) sets another bound per call. The result and the errors are as before: one failed request still rejects the whole call, and no request is started after it. A custom `NetworkProvider` implementation may take the new parameter.
- `getHistory` on a wallet no longer sends a `blockchain.address.get_balance` request per address to backfill the running balances: it takes the current balance from the wallet's utxos, the satoshis of token coins included as before, so the numbers are the same. The standalone `getHistory({ addresses, provider, … })` takes the new `utxos` (the current utxos of `addresses`) for the same; without it, it reads the balance per address as before. Every fan-out of a history load (the history per address when no `rawHistory` is given, the transactions, the headers, the spent outputs, the balances) now keeps at most 10 requests in flight, one step after the other; the new `concurrency` option of the wallet `getHistory` and of the standalone function sets another bound. A single-address wallet's `getHistory` now waits for its status watch and the fetch it triggered, as `getBalance` does.
- Reading a transaction with its input values (`getRawTransaction(hash, true, true)`, `getRawTransactionObject(hash, true)`, `decodeTransaction(hash, true)`) now fetches the spent transactions at most 10 at a time instead of all at once; a transaction with many inputs, such as a consolidation of the wallet's coins, put one request per input on the socket together. The result and the errors are unchanged.
- Single-address and watch-only wallets keep their cache (status, utxos, history) in memory only, as mainnet-js 3.1.7 did. next.14 wrote it to a `walletCache-…` record per wallet, the private key included, a second copy of the key the wallet's database row already holds, and one that a rollback to 3.1.7 would leave behind. Such a wallet now fetches its utxos and history once after it is constructed, as in 3.1.7. `purgeWalletCache`, `pruneWalletCaches` and `deleteNamedWallet` find no record of theirs to remove, and `pruneWalletCaches` removes a record an earlier version wrote for one, as it does every record of a wallet not kept.
- Everything the library throws, and every promise it rejects, is now an `Error`. `signUnsignedTransaction` threw libauth's error string for a transaction that does not decode and libauth's array of generation errors when it could not sign; it now throws an `Error` with libauth's message, and for a signing failure "Could not sign the transaction: …" with libauth's errors as `cause`. `getHistory` (and the wallets' `getHistory`) threw libauth's string for a transaction from the server that does not decode, and the transaction building behind `send` and the token operations threw a string for an input address that does not decode or tokens that do not add up; these are `Error`s with the same message. A caller with a `typeof error === "string"` branch for these can drop it and read `error.message`.
- New export `BroadcastRejectedError`, thrown by `sendRawTransaction`, and so by `submitTransaction`, `send`, `sendMax` and the token operations, when the server refuses the transaction. `reason` is the node's reject reason (e.g. `"txn-mempool-conflict"`, `"Missing inputs"`, `"dust"`, without BCHN's debug message), `code` BCHN's reject code when the server gives one (18 for a mempool conflict, none for `"Missing inputs"`), `txid` the refused transaction's id and `cause` the server's error. The message is still the server's text ("the transaction was rejected by network rules.\n\ntxn-mempool-conflict (code 18)\n"), so matching on it keeps working, but tell a refusal apart with `instanceof BroadcastRejectedError` and branch on `reason`. `alreadyKnown` is true when the answer is that the node already holds the transaction (`"txn-already-known"`, `"txn-already-in-mempool"`, `"transaction already in block chain"`): an earlier broadcast of it went through, so a caller must not report it as a failed payment, or the user may pay again. A broadcast that times out stays an `ElectrumTimeoutError` and one that loses its connection a plain `Error`: neither is a refusal, as the transaction may have reached the node. A `Transport` other than `ElectrumTransport` should give a server's error response its JSON-RPC `code` and `message`, on the Error or on its `cause`, for the provider to recognise it, and a connection error must not have that shape; a DOMException or a CloseEvent cause, which carry a numeric code, is not taken for a server's answer.
- A token `send` with several mutable NFT requests whose commitments the wallet does not hold spends one mutable NFT per request, as it already did for requests matching an NFT exactly. Every such request after the first took the mutable NFT the first had picked, and the transaction then failed the token check ("…creates more mutable tokens than are available…") while the wallet held enough of them. A send with more such requests than the wallet has mutable NFTs of the category now throws `InsufficientFundsError` ("No suitable token utxos available…") before anything is built. Minting NFT requests are unchanged: a minting NFT the send already spends backs any number of new minting NFTs, as consensus allows. A new mutable NFT is now backed the same way by a minting NFT of its category that the send spends, whatever the order of the requests, instead of consuming one of the wallet's mutable NFTs and destroying its commitment; a mutable NFT such a send spends anyway, for its fungible tokens or through `ensureUtxos`, comes back as change with its commitment.
- `HDWallet.fromId` restores an `hd:<network>:<xprv or tprv>:<depositIndex>:<changeIndex>` walletId, the form `toDbString` writes for a wallet made with `fromXPriv`. It read the key as a mnemonic and threw "Invalid mnemonic, must be 12 or 24 words", as mainnet-js 3.1.7 does, so such a wallet could be serialized but not restored, and `replaceNamed` refused its id. The id formats are unchanged; mnemonic and xpub ids parse as before.
- An empty key no longer makes a wallet with a new random key: `fromWIF("")`, a `wif:<network>:` walletId (or one without its key part), `HDWallet.fromSeed("")`, `HDWallet.fromXPriv("")`, `HDWallet.fromXPub("")` and an `hd:<network>:` walletId now throw an `Error` ("refusing to create wallet from empty WIF", "… from empty mnemonic", "… from empty xPriv", "… from empty xPub", "… from a walletId without a key"), as `fromSeed("")` of a single-address wallet already did. The other id forms with their value missing throw a clear `Error` instead of a `TypeError` or "Could not initialize wallet - insufficient parameters": `privkey:` ("refusing to create wallet from empty private key"), `seed:` ("refusing to create wallet from empty mnemonic"), `watch:` ("address is required to create a watch-only wallet") and `named:` ("Named wallets must have a non-empty name"). A caller that wants a random wallet calls `newRandom`.
- Every spend now draws its coins from one pool: the wallet's current coins, narrowed to `options.utxoIds` when given, minus the new `options.excludeUtxoIds` (`string[] | Utxo[]`, the forms `utxoIds` takes; ids the wallet does not hold are ignored, the txid matches in either case, and an id that is not a `txid:vout` outpoint, such as a bare txid, throws `InvalidRequestError` with `field` `"excludeUtxoIds"` and `value` the id as given, rather than leave the coin it meant spendable). `send`, `sendMax`, `getMaxAmountToSend`, `tokenGenesis`, `tokenMint` and `tokenBurn` honor it: an excluded coin is never an input, not as a BCH coin the selection picks, a token coin a fungible send needs, the input of an NFT request, a genesis input, a minting NFT or a burned token, and it is never shown to a `coinSelection` hook; `getMaxAmountToSend` reports the max over that pool. A coin listed twice in `utxoIds` is one coin of the pool, at the place of its first listing; before, `tokenBurn` counted its satoshis (and its tokens) twice in the token change it built. A caller that subtracted its reserved coins from `getUtxos()` to pass the rest as `utxoIds` can pass them as `excludeUtxoIds` instead. A coin in `options.ensureUtxos` must be in the pool: one that is excluded, outside the given `utxoIds` or not in the wallet now throws the new export `UtxoNotAvailableError` before anything is built, with `utxoId` (`txid:vout`) and `reason` (`"excluded"`, `"not-in-utxoIds"` or `"not-found"`). Before, `ensureUtxos` went into the transaction unchecked, so a caller who passed an `ensureUtxos` coin outside its `utxoIds` (or a coin the wallet no longer holds) now gets that error and has to add the coin to `utxoIds`. `tokenGenesis`, `tokenMint` and `tokenBurn` still pick their inputs themselves and do not spend `ensureUtxos`, but refuse a coin there outside the pool all the same. An `ensureUtxos` coin is compared by outpoint and spent as the wallet's own copy of it, so the satoshis and token data the caller's object carries no longer count.
- A `coinSelection` hook may only pick from the coins it is given in `available` (or `pinned`, which are spent anyway): a pick outside them, such as an excluded coin or one from a list the hook kept itself, now throws `InvalidRequestError` with `field` `"coinSelection"` and `value` the pick's `txid:vout`, and a picked coin is spent as the given one, whatever satoshis the returned object carries. An `inputOrdering` hook must return a permutation of its `inputs`: one that adds, drops or repeats a coin now throws `InvalidRequestError` with `field` `"inputOrdering"` and `value` that coin's `txid:vout`. Before, both went into the transaction as returned. The built-in strategies of `bch-wallet-lib/coin-control` already do this and are unaffected.
- `sendMax` and `getMaxAmountToSend` refuse a token coin in `options.ensureUtxos` with `InvalidRequestError` (`field` `"ensureUtxos"`, `value` the coin's `txid:vout`) before anything is built. The max counted only the BCH coins while `sendMax` spent the token coin as well: its tokens came back as change and the rest of its satoshis went to the miners, so a 50,000-satoshi token coin paid a fee of about 49,000 satoshis. A caller that wants a token coin's satoshis swept sends its tokens away first, or uses `send`. BCH coins in `ensureUtxos` are spent as before, as the first inputs.
- Every transaction `send`, `sendMax`, `tokenGenesis`, `tokenMint` and `tokenBurn` build is checked, before it is signed, for tokens its outputs destroy: per category the outputs must carry the inputs' fungible amount, and every NFT input must come back as it was or as the CashTokens rules let it change (a minting NFT as another minting NFT; a mutable one, when no minting NFT of its category is spent, with another commitment or as an immutable NFT). Only what a `tokenBurn` request names and the fungible tokens `tokenMint(…, deductTokenAmount = true)` takes off its minting NFT may go. Otherwise the new export `TokenBurnError` is thrown, with `category`, `amount` (the fungible tokens missing, `0n` when an NFT is) and `nft` (the missing NFT's `capability` and `commitment`), and nothing is built, broadcast or returned unsigned. Before, only tokens created from nothing were refused, so an `outputOrdering` hook that dropped the token change (or a regression in the change) burned tokens silently. `checkTokenQuantities: false` turns the check off, for the token operations as well; callers whose own hooks keep every output need no change.
