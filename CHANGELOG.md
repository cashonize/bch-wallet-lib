# Changelog

## 0.1.3 (unreleased)

- With `Config.UseIndexedDBCache`, a cache connection dropped while a fetch was out no longer fails the fetch with "Database is not initialized" (a 0.1.2 regression): the provider opens the cache again before writing, and a cache write that still fails is ignored.

## 0.1.2 (2026-10-21)

- With `Config.UseIndexedDBCache`, the provider opens its IndexedDB cache once instead of before every request, and opens it again after the connection is lost. A provider whose first call reads the cache (`getRawTransactions`, `getHeaders`, `getRawTransaction`, `getRawTransactionObject`) no longer fails with "Database is not initialized".
- An HD wallet's address discovery starts where its cache saw the wallet used (at most 2000 addresses per branch), watching the used range in one round instead of about 20 addresses per round trip from index 0. `indices` therefore holds that value right after construction, before discovery has run; the cache format is unchanged.
- During discovery, a used address extends the watched window as soon as its status arrives, and counts as used even when the fetch of its coins fails.
- Discovery, and `setProvider` moving a wallet's subscriptions, take at most 50 address subscriptions or fetches at a time per wallet, where they started all at once.
- A history load (`getHistory`) keeps up to 32 requests in flight by default, where it kept 10; pass `concurrency` to change it.
- A send returns sooner: `sendRawTransaction` broadcasts before subscribing to the transaction, and a send's wait for its coins skips the HD wallet's 100 ms debounce and any address discovery under way. A subscription that cannot be made no longer rejects `sendRawTransaction`; a lookup of the transaction decides (its txid when the server holds it, a `BroadcastTimeoutError` when not).

## 0.1.1 (2026-10-20)

- A closed transport, and so a disconnected provider (`provider.disconnect()`), refuses to connect again: a request or subscription made on it afterwards rejects with "The electrum transport was closed.", where it used to open a new connection to the same server. A request still in flight on a provider the caller replaced, e.g. a history load during a server change, no longer reconnects to the server the caller left. A caller that disconnected a provider to connect again later makes a new provider instead.
- The client name sent to electrum servers in `server.version` is `@cashonize/bch-wallet-lib`, the package's name, where it was `bch-wallet-lib`.

## 0.1.0 (2026-10-20)

Starting point: mainnet-js `4.0.0-next.14` (`next` @ `9ec2a0e`), plus mainnet-js#244 (128-byte NFT commitments).

### Changes for callers coming from mainnet-js

- `Config.DefaultParentDerivationPath` is `m/44'/145'/0'`, BCH's coin type, where mainnet-js used Bitcoin's `m/44'/0'/0'`: a new wallet made without a path, and a wallet id without one (`seed:<network>:<mnemonic>`, `hd:<network>:<mnemonic>`), now derive under `145'`, so the same mnemonic without a path gives other addresses than before. A stored id is unaffected, as `toDbString` writes the path into every mnemonic id, and mainnet-js 3.1.7 did too. A caller that relied on the old default passes the path or sets the config back to `m/44'/0'/0'`.

- Package name `@cashonize/bch-wallet-lib`; `@mainnet-cash/indexeddb-storage` is now the `@cashonize/bch-wallet-lib/indexeddb` subpath export.
- The CLI (`src/cli.ts`) and the browser bundle are not shipped.
- The Electrum transport is `@electrum-cash/network` with `@electrum-cash/web-socket` instead of `@rpckit/*`:
  - Servers are plain URLs, `wss://host:port` or `ws://host:port`. `createProvider(network, servers?, options?)` and `DefaultProvider.servers.<network>` take one URL, several separated by commas, or an array. A list is tried in order when connecting, and the provider stays with the first server that connects: after a failure electrum-cash reconnects to that server and restores its subscriptions there. rpckit's notation (`fallback(...)`, `?timeout=…&batchSize=…` options) is rejected with an Error, and requests are no longer batched.
  - `ElectrumNetworkProvider` is no longer generic over an rpckit schema, and its constructor takes the library's internal transport (the interface of what the provider needs: `connect`, `close`, `request`, `subscribe`): build a provider with `createProvider`. `performRequest<T>(method, params)` and `subscribeRequest(method, params, callback)` take the result type from the caller instead of the schema, and are protected (see Changed).
  - Every server gets a connect timeout (10 s) and a request timeout (30 s), a single user-supplied URL included (mainnet-js#251); `ElectrumTransportOptions` (`connectTimeout`, `requestTimeout`, in ms) is the third argument of `createProvider`. A timed out request rejects with an `ElectrumTimeoutError`, no longer with the string `"electrum-cash request timed out, retrying"`. Errors are always `Error` objects.
    - Retry: a request that times out or loses its connection is sent once more, on a (re)connected server, where it used to be awaited again on the same one. If the first send's answer still arrives before the second's, it is taken. A broadcast is never sent again, nor is a request the server answered with an error.
    - Dead connections: a connection that stays silent after a send for half the request timeout, or for the connect timeout if that is shorter (10 s with the defaults), is taken for dead and replaced, so that a re-sent request goes to a fresh connection rather than the dying one, e.g. after iOS / Safari dropped the socket of a backgrounded page.
    - Caps: that same shorter value is the socket's own timeout, which also bounds opening the socket, so a `connectTimeout` above half the `requestTimeout` does not give a server longer to connect (`connectTimeout: 20_000` with the default request timeout still gives up after 15 s), and a `requestTimeout` above twice the `connectTimeout` does not make a silent connection last longer.
  - In a browser the socket stays connected while the page is hidden and ignores online/offline events; it reconnects when the connection actually fails. In Node, TLS certificates are verified.
  - Protocol version 1.5 is asked of every server (mainnet asked for 1.6), as electrum-cash only accepts the exact version it asks for and chipnet servers stop at 1.5.
  - `daemonPassthrough()` is removed: Fulcrum's `daemon.passthrough` takes named params, which electrum-cash cannot send. The regtest `provider.mine` (marked `@internal`) calls the node's RPC directly, with the `RPC_*` environment of the regtest (as mainnet-js 3 did).
  - New exports: `ElectrumTimeoutError` and the type `ElectrumTransportOptions`.
- The HD wallet cache keeps its record in mainnet-js 3.1.7's form again: entries keyed `${walletId}-${index}-${change}`, each with its `index` and `change`, and an `indexCache` from address to `{ index, change }`. next.14 had rekeyed it to `${walletId}-${path}` with a `pathCache`, so it ignored the cache of every wallet 3.1.7 had opened (and dropped those entries on load, rewriting the record), and 3.1.7 ignored its cache after a rollback. A wallet opened on what 3.1.7 wrote now reuses those addresses, statuses, utxos and history and writes nothing on load, and 3.1.7 reuses what the library writes. Only branches 0 and 1 have a place in that form: addresses on other branches are cached in memory only. Entries in next.14's form are not read, and are dropped at the next write (mainnet-js#251).
- `GAP_SIZE`, `DEPOSIT_BRANCH` and `CHANGE_BRANCH` are exported from the entry again, as in mainnet-js 3 (mainnet-js#251).
- `sendMax`, `send` and the token operations no longer write to the caller's options object (`sendMax` set `options.utxoIds`, a token send appended to `options.ensureUtxos`), so reusing an options object, e.g. for a retry, no longer carries the previous inputs forward (mainnet-js#251).
- New export `InsufficientFundsError`, thrown wherever the wallet's coins (or the given `utxoIds`) cannot cover a send, a genesis, a mint or a burn, with `asset` (`"bch"` or `"token"`) and, for a token, its `category`; tell it apart with `instanceof` instead of matching messages. The messages are unchanged: "Amount required was not met…", "There were no Unspent Outputs", "The available inputs couldn't satisfy the request with fees", "The available inputs in the wallet cannot satisfy this send request", "Insufficient funds for transaction given fee", "Not enough vout=0 inputs available for new token genesis…", "Not enough token amount to send", "No suitable token utxos available to send token…", "You do not have any token UTXOs with minting capability…", "You do not have suitable token UTXOs to perform burn…" (mainnet-js#251).
- New `wallet.setProvider(provider)` switches an existing wallet to another electrum provider of its network: the wallet's subscriptions (status watches, an HD wallet's address discovery and `watchBlocks`) are made again on the new provider and ended on the old one (mainnet-js#251). The old provider is left connected, as other wallets may still use it: once `setProvider` resolves, the caller disconnects it if nothing else uses it. If the new provider cannot connect, or a subscription cannot be made there, `setProvider` rejects and the wallet stays on the old provider with its subscriptions; a retry with the same provider tries again. If the old provider also fails while the subscriptions that did move are moved back, those stay on the new provider until the next `setProvider` call moves them, so call it again. Moved status watches get the new server's current status, as when they start, so a `watchBalance` callback may fire with an unchanged value (an HD wallet's status watches fire once per watched address); a moved `watchBlocks` callback gets the new server's tip only if it differs from the last header it saw. `wallet.provider` is now a getter: assigning it (the old workaround, under a `@ts-ignore`) throws a `TypeError`, so call `await wallet.setProvider(provider)` instead.
- `wallet.stop()` now also ends `watchBlocks` subscriptions, which it left running before, and a subscription still being made when `stop()` runs (e.g. a `watchBlocks` called just before it) is ended once it is made, where it stayed live before. The protected `cancelFns` / `trackCancelFn` are replaced by the protected `subscribe(fn)`.
- An HD wallet stopped while its address discovery is still extending the watched range now subscribes no further addresses. It went on to the next round, whose subscriptions `stop()` no longer reached: a wallet switched away from during its first discovery kept about 20 more addresses per round subscribed, fetching and writing its cache, for the rest of the session.
- An HD wallet's `stop()` now makes the cache write it had scheduled (they are debounced by 2 s) before it resolves, where the write came up to 2 s after `stop()`; a write that fails does not make `stop()` reject.
- A subscription that cannot be made (e.g. the server is unreachable) no longer leaves what waits on it pending forever (part of mainnet-js#256): `sendRawTransaction`, which waits on a subscription of its own, rejects with the error, and the wallet's reads reject as the next entries say.
- An HD wallet's address discovery now settles when an address's subscription or its first fetch fails (mainnet-js#256); it hung before, with an unhandled rejection. `getUtxos`, `getBalance` and `getRawHistory` reject with that error, and the next of them runs discovery again first, subscribing the addresses that failed, so a wallet constructed offline recovers once a read succeeds and no longer needs rebuilding. Reads only retry the default gap, and the gap maintenance subscribes the missed addresses once used addresses bring them inside it. After `stop()` reads no longer retry, they reject with the last error. A fetch that fails after discovery, on a later status notification, leaves that address's state as it was until its next notification fetches again, without an unhandled rejection. `watchBalance` and `watchTokenTransactions` skip a notification whose read fails (e.g. while a gap extension has failed), and report the error as below, instead of producing an unhandled rejection.
- A single-address or watch-only wallet whose status subscription or first fetch fails now does what an HD wallet's discovery does (mainnet-js#256): `getUtxos`, `getBalance`, `getRawHistory` and `getHistory` reject with the error, and the next of them subscribes again, so a wallet constructed offline recovers once a read succeeds. Before, a failed subscription let them go on with the cached (or empty) state, and a failed first fetch did the same without any error. After `stop()` reads no longer retry; they reject with the last error. A fetch that fails on a later notification leaves the wallet's state and status as they were, so the next notification fetches again; the status of the failed fetch used to be taken as current, which kept the stale state until the address changed again. Status watchers are now called once the notification's fetch is done instead of before it. Callers that read right after constructing a wallet must handle the rejection; calling the read again retries.
- `getRawTransactionObject` with `Config.UseIndexedDBCache` no longer reports a transaction it first fetched from the mempool as unconfirmed forever. The cached entry's confirmations were only brought up to date when above 0, so one cached at 0 stayed at 0, without its block hash and time, across reloads. An entry cached unconfirmed is now fetched again, which also heals the entries mainnet-js left at 0 in the same cache.
- A transaction the server returns (`getRawTransaction`, `getRawTransactions`, `getRawTransactionObject`) is checked against the txid it was asked for, and refused with an error when its hex hashes to another txid. It was cached under the txid asked for unchecked, so a malicious or broken server could plant a fake transaction in the IndexedDB cache, where it outlasted a switch to an honest server (history amounts and addresses, NFT parsing). The decoded fields of a verbose transaction are still the server's.
- A fetch of an address's coins and history that fails after the first, on any wallet type, no longer leaves the old state in place until the address changes again or the socket reconnects: the next `getUtxos`, `getBalance`, `getRawHistory` or `getHistory` fetches the address again, and rejects with the error if that fails too, as after a failed first fetch. Before, the old state was read as current, so coins received meanwhile stayed invisible, and an HD wallet kept handing out that address as unused.
- Of two fetches for one address, the one a newer notification started is the one applied: an older fetch whose answer comes last no longer overwrites the newer state.
- Watch callbacks may be async, and their errors are reported the same way on every wallet type: a callback's throw or rejected promise, and a read the watch makes for it that fails (the balance read of `watchBalance`, the history and transaction reads of `watchTokenTransactions`), goes to `console.error`, and the watch goes on. Before, it was dropped silently (an HD wallet's watchers, a single-address wallet's throwing callback) or became an unhandled rejection, which ends a Node process by default (a single-address wallet's async callback, `watchBlocks`, the provider's subscriptions). A callback passed to the provider's `subscribeToAddress`, `subscribeToTransaction`, `watchAddressStatus` or `watchBlocks` is handled the same way. The new transactions of one notification are reported each on its own, so one that fails no longer keeps the next from being reported. Callback types return `unknown` instead of `void`, so an async callback type-checks under `no-misused-promises`; wrappers that only exist to turn an async callback into a void one can go. A caller that needs a callback's error catches it in the callback.
- `sendRawTransaction` for a transaction the server already knows now ends its subscription, which it left running.
- A wallet cache write that fails (e.g. storage full) and an exchange rate that cannot be cached no longer surface as unhandled promise rejections, which end a Node process by default; the cache write is redone by the next one, and the rate is still returned.
- The fee rate is no longer read from or cached in the globals `BCH_RELAY_FEE` / `tBCH_RELAY_FEE` / `rBCH_RELAY_FEE` (BCH per kB): set the new `Config.RelayFeePerByte` (satoshis per byte) instead, e.g. `Config.RelayFeePerByte = 1` for `globalThis.BCH_RELAY_FEE = 0.00001`; it applies to every network. Without it, the server's `blockchain.relayfee` is cached per provider rather than process-wide, so a wallet moved to another server with `setProvider` uses that server's rate (mainnet-js#254).
- The server's `blockchain.relayfee` is checked against a cap of 10 sat/byte: a server rate above it is taken as untrusted and ignored, and sends pay 1 sat/byte (the network's relay minimum), with a console warning. It was used unchecked, so a server could make every send pay any fee it chose; clamping it to the cap instead would still let a hostile server make every send pay 10 times the minimum. A caller that wants a higher rate sets `Config.RelayFeePerByte`, which the cap does not bound. The fee rate is never below 1 sat/byte, the network's relay minimum, whatever the server reports or the settings say (a missing, non-finite or lower server rate gives 1 sat/byte; so does a `Config.RelayFeePerByte` below 1, which was used as given and built transactions that do not propagate). `Config.RelayFeePerByte` must be a finite, non-negative number: anything else (`NaN`, a negative number, `Infinity`, a string) makes every send reject with an `Error` naming the setting, before anything is built (mainnet-js#254).
- `watchTokenTransactions` reports only transactions that are new after the watch started, each once, for single-address and HD wallets alike (mainnet-js#257). It replayed the whole history as new when the first new transaction arrived, mixed in with it. A caller that pre-seeded a dedupe set from `getRawHistory()` can drop it; one that relied on the replay reads `getRawHistory()` before watching. The set of known transactions is taken when the watch is set up, so start it before the send it should see.
- An NFT input or output given without a `commitment` (only possible from untyped code) now gets empty commitment bytes in the libauth transaction instead of `false`; the encoded transaction is unchanged.
- The first exchange rate fetched outside the browser cache (in Node, or in a browser whose localStorage throws) is now cached for the TTL like later ones; it was not stored, so the next conversion fetched again (mainnet-js#262).
- Cached exchange rates follow `Config.GetExchangeRateFn`: once it is set to another function, the rates cached from the previous one are no longer served, nor is a rate that was still being fetched from it when it changed; the first conversion after the switch fetches from the new source. Assigning a new function is all a caller does, nothing needs clearing. A change is noticed by the next rate lookup, so switching away and back before any lookup keeps the cache. Until the first change in a process, rates cached by an earlier run (mainnet-js 3's included, whose `rate-<symbol>` entries keep their key and shape, now with a `source` field added) are still used. In a browser, a rate fetch that fails no longer fetches a second time through the in-memory cache; the error is thrown directly.
- New `ExchangeRate.getQuote(symbol, { staleOnError? })` returns `{ symbol, rate, fetchedAt, stale }` (`fetchedAt` in ms since the epoch), with the new types `ExchangeRateQuote` and `ExchangeRateOptions`. A rate is cached for its TTL, and a fresh one fetched after it. With `staleOnError: true`, a fetch that fails returns the last cached rate of the current source for that symbol, however old, as `stale: true`, instead of throwing; check `fetchedAt` to decide whether it is still good enough. Without a cached rate it throws the fetch's error. Without the option, and in the conversions, a failed fetch throws as before. It replaces `ExchangeRate.get` (see Removed).
- `getHistory` no longer throws on an output or a spent input whose locking bytecode has no CashAddress (P2S, P2PK, bare multisig); its `address` is `SCRIPT: <hex>`, as an OP_RETURN output's is `OP_RETURN: <hex>` (mainnet-js#252). Every input and output now carries its `lockingBytecode` (hex), and every input its spent `outpointTransactionHash` and `outpointIndex` (mainnet-js#248); a coinbase input has none of these.
- `SignedMessage.verify` matches the address by its decoded payload and type instead of by string: an uppercase or prefix-less cashaddr of the signing key now verifies (a given prefix still has to be the address's own, which its checksum checks), and only a P2PKH address (with or without token support) can match; a P2SH address with the key's hash as its payload matched before. It no longer throws on a signature that is not base64, has a recovery byte outside 31..34 or recovers no key, nor on an address that does not decode: it returns `valid: false` (with `signatureValid: false`, or `publicKeyHashMatch: false` for the address). The result shape is unchanged; callers that lowercased the address or caught throws can drop that.
- `OpReturnData.fromArray` and `fromString` build OP_RETURN scripts up to the standard 223 bytes (the whole script, the `OP_RETURN` and push opcodes included); they refused more than 220, so standard outputs of 221 to 223 bytes threw. Pushes of 76 to 255 bytes use `OP_PUSHDATA1`; the error is now "OP_RETURN script can not exceed 223 bytes in size". A send whose OP_RETURN outputs add up to more than 223 bytes, the limit BCHN applies to the sum over a transaction, now throws "OP_RETURN outputs can not exceed 223 bytes in total, got N" before anything is broadcast, instead of being refused by the node as `oversize-op-return`. The limit is exported as `MAX_OP_RETURN_BYTES` (mainnet-js#260).
- `OpReturnData.parseBinary` reads every push of the script: it stopped at the first empty push (`OP_0`), dropping every later chunk, and read `OP_1NEGATE` and `OP_1`..`OP_16` as pushes of 79 and 81 to 96 bytes. An empty push now gives an empty chunk, `OP_1NEGATE` the byte `0x81` and `OP_1`..`OP_16` the bytes `0x01`..`0x10`. It now throws on what it misread silently before: a script that does not start with `OP_RETURN`, a non-push opcode, or a push longer than the bytes left; callers reading untrusted outputs should catch that (mainnet-js#260).
- `send`, `sendMax`, `tokenGenesis`, `tokenMint` and `tokenBurn` now also return the transaction they broadcast, as hex in `transaction`, as a `broadcast: false` send already did (mainnet-js#245). A `SendResponse`'s `txId`, `transaction` and `categories` are always set, so `response.txId!` needs no assertion.
- `fromWIF` and `fromId("wif:…")` errors no longer contain the WIF (mainnet-js#258). The WIF is now decoded and checked by its version byte instead of its first character: a WIF of the other network fails with "WIF is for testnet, expected mainnet" (or the reverse), replacing "Mainnet type wif … passed, should start with L or K"; a malformed one with "Invalid WIF: …". Uncompressed WIFs (mainnet `5…`, testnet `9…`) are rejected with "Uncompressed WIF private keys are not supported" on every network: the wallet only derives and signs for the compressed public key's address, which does not hold an uncompressed key's funds, and regtest wallets used to accept them onto that wrong address. Regtest wallets still accept compressed WIFs of either version byte.
- `fromId` and `named`/`replaceNamed` (with a stored or given walletId) no longer quote a walletId part they cannot place, which for an id missing its network part (`wif:<key>`, `seed:<words>`) or with no colons at all (a bare WIF) was the key itself: such an id now fails with "Unknown network prefix to a mainnet wallet", instead of a `TypeError` naming the part. "Network prefix regtest to a testnet wallet" is unchanged for a known network. A watch-only wallet's `fromId` checks the network part before the wallet type.
- `tokenMint` and `tokenBurn` honor `options.utxoIds` as `send`, `sendMax` and `tokenGenesis` do: the minting NFT and the tokens to burn are taken from the given utxos only, and an id not in the wallet throws `UtxoNotAvailableError` (mainnet-js#250). Before, they picked their token inputs from all of the wallet's utxos and pinned them to the transaction, so a coin outside `utxoIds` could be spent; a mint or burn with no suitable token among the given utxos now throws `InsufficientFundsError`.
- `tokenMint` re-creates the minting NFT at a change address of the wallet, as `tokenBurn` does with its remainder, instead of at the address it was spent from (mainnet-js#259). An HD wallet's minting NFT therefore moves to a fresh change address with every mint rather than staying on one address; single-address wallets are unaffected.
- In an HD wallet, the NFTs minted by one `tokenMint` call and the tokens created by one multi-request `tokenGenesis` that are given no `cashaddr` each go to their own unused token deposit address instead of all to the same one (mainnet-js#259). They take the next unused addresses in the order of the outputs: for `tokenGenesis` the order of its requests, for `tokenMint` its requests grouped by category, the categories in the order they first appear and each category's requests in their order. A single default output still goes to `getTokenDepositAddress()`; single-address wallets are unaffected.
- A token `send` now builds its token change from the token inputs it spends minus the requested token outputs, per category and per NFT (mainnet-js#247). Every spent NFT no request sends comes back at a change address with its own satoshi value and, as far as the category's fungible change covers it, its own fungible amount; the rest of the fungible change goes to one fungible-only output, after the NFT ones, holding the standard 1000 sats of a token output. mainnet-js gave that output the `value` of the first token request, so a token sent with more satoshis (an NFT sent with 20000 sats, say) locked as many again in the change, taken out of the BCH change. Before, the change copied the NFT of the first request of the category: a fungible send burned the NFT of a hybrid coin it spent (e.g. a minting NFT that also held fungible tokens), sending a minting NFT left a copy of it on the fungible change, sending a mutable NFT with a new commitment built a transaction the network rejects, and an immutable NFT could not be sent at all ("No suitable token utxos available…") while the wallet held fungible tokens of its category. A token coin passed in `ensureUtxos` whose category the send does not name now comes back as change too, where it was burned; `checkTokenQuantities: false` still builds no token change. Token change a caller builds itself, as a workaround, still works (the library then finds nothing left over) and can be dropped.
- A fungible token `send` now spends only the coins of the category its amount needs, instead of every coin of the category holding fungible tokens (mainnet-js#246), which linked every address of an HD wallet that ever received the token and grew the transaction with the holding. The fungible tokens on the coins the send spends anyway (`ensureUtxos` and the inputs of its NFT requests) count first; the rest is taken from fungible-only coins, largest first, and only when those fall short from NFT coins holding fungible tokens, largest first, whose NFT comes back as change. The token change is computed from exactly the spent coins, so nothing is burned implicitly; a send whose selection would spend a token coin the change does not account for throws instead of building the transaction. A send of NFTs alone no longer spends the fungible coins of their category, and the change outputs of a send over several categories now come in the order of the coins spent (the NFT requests' inputs first). A caller that relied on a send consolidating its token coins can send the holding to itself, or pass the coins in `ensureUtxos`. The satoshis of the token coins a send no longer spends no longer pay for it either, so a wallet holding only token coins needs plain BCH coins for the fee and the token change: sending 5 of the tokens of one of three 1000-sat coins pinned all three and paid from their 3000 sats, and now throws `InsufficientFundsError` ("Amount required was not met…", `asset: "bch"`). The shortfall checks also run in another order: a fungible token send from a wallet with no coins (or none among `utxoIds`) throws "There were no Unspent Outputs" (`asset: "bch"`) instead of "Not enough token amount to send" (`asset: "token"`), and a send that is short of both an NFT and fungible tokens reports the NFT ("No suitable token utxos available…") instead of the fungible amount.
- The fee that a send's coin selection has to cover is now estimated from the coins it selects instead of from every coin it could spend (mainnet-js#253): the selection is run again for the fee of the coins it picked until they cover their own fee, the exact fee of the built transaction included. Sizing every coin as an input made `tokenGenesis`, `tokenMint`, `tokenBurn` and token `send`s fail with "Amount required was not met" in wallets holding many token coins and little BCH (each token coin the operation does not spend asked for about 190 sats at 1 sat/byte), and made plain sends spend more coins than they need (sending 4500 sats from 100 coins of 1000 sats took 20 inputs instead of 6). When the coins fall short, the amount in that error, and in its `required`, is now the outputs plus the fee of spending every coin the send could use (the pinned coins and the BCH coins of the wallet, or of `utxoIds`), no longer counting the token coins it would not spend; or the amount its last selection asked for, if that is more. When the selected coins would leave a change at or below dust, which is not built and goes to the miners, the selection is redone for a change above dust, and that selection is used if it pays the miners less (a 9000 sat send from 20 coins of 1000 sats now spends 12 coins and gets 1229 sats of change back, where 11 coins would have paid 2000 sats for a 1595 byte transaction). `getMaxAmountToSend` already sized only the coins it counts and is unchanged, and `sendMax` still spends every one of those coins, also those worth less than their own input fee (possible above about 3.7 sat/byte), which the new selection would have left unspent.
- `getNamedWalletId(name, dbName?)` is exported from the entry again, as in mainnet-js 3, and now does what its type says (mainnet-js#261): a name with no record returns `undefined` instead of throwing "No record was found…", and without `dbName` it reads the mainnet database (`"bitcoincash"`), where `named()` stores mainnet wallets, instead of handing the storage provider `undefined` (which `IndexedDBProvider` turned into a `"wallet"` database). It still throws when no `StorageProvider` is configured.
- New export `pruneWalletCaches(keepWalletIds)` removes the cache record of every wallet but the given ones from the cache storage `Config` selects, e.g. records left by wallets deleted earlier (part of mainnet-js#249). A record holds an HD wallet's derived private keys along with its status, utxos and history. Pass the stored id (`toDbString()`, a database row's `wallet`) of every wallet that is kept, from all databases; the records are worked out from them without constructing a wallet, so no provider is created. A kept id it cannot read (the check `deleteNamedWallet` makes) is skipped and keeps no record, since no wallet class loads it, and the other records are pruned as usual; it resolves to the positions in `keepWalletIds` of the ids it skipped (`[]` when it read them all), so a caller can report them.
- New export `deleteNamedWallet(name, dbName?)` deletes a named wallet's row and its cache record, so its private keys do not outlive it (mainnet-js#249); `StorageProvider.deleteWallet` still removes only the row. Like `getNamedWalletId`, it reads the mainnet database (`"bitcoincash"`) without `dbName`, and works through whatever `BaseWallet.StorageProvider` is. It removes the cache record before the row, and works out the record before removing either: a row whose wallet id cannot be read (e.g. a `named:` alias), or a record that cannot be removed, makes it throw with the row kept, so it can be retried. A loaded wallet need not be stopped first: once the call resolves, no wallet of that id made before it, or opened from the row while it ran, writes the record again; they keep their cache in memory only (a wallet made later, e.g. the same seed imported again, caches as usual). A removal that fails leaves those wallets writing it. This holds within one JavaScript process: a wallet of that id open in another browser tab can still write the record back; `pruneWalletCaches` at a later start removes it.
- New export `InvalidRequestError`, with the request `field` (`category`, `nft.commitment`, `amount` or `nft`) and the `value` given, thrown by the `TokenSendRequest`, `TokenGenesisRequest`, `TokenMintRequest` and `TokenBurnRequest` constructors, and by `send`, `tokenGenesis`, `tokenMint` and `tokenBurn` for plain request objects before they read a coin, when the token data cannot go on chain as given. A category must be 64 hex characters (`tokenMint` and `tokenBurn` threw a plain "Invalid category supplied…" `Error` for a wrong length, `send` read any string); a commitment must be an even number of hex characters and at most 128 bytes, where libauth's `hexToBin` read `"abc"` as `ab0c` and `"test"` as other bytes, so a typo built a different commitment than asked; a fungible amount must be an integer from 0 to 2^63-1 (bigint, number or digit string; a negative burn amount counted as 0 before); and a token send or genesis output needs a positive amount or an NFT, as does every mint request: such an output was built as a plain BCH output to the token address, its token data dropped. Callers that passed a text commitment convert it to hex first (e.g. `binToHex(utf8ToBin(text))`). `tokenMint`'s docs now say that every request creates one output and that the library caps neither the number of requests nor the outputs.
- `ElectrumNetworkProvider.getRawTransactions` and `getHeaders` keep at most 10 requests in flight for their cache misses, instead of sending them all at once; the new last parameter `{ concurrency }` sets another bound per call, a positive integer or `Infinity` for no limit. The result and the errors are as before: one failed request still rejects the whole call, and no request is started after it.
- `getHistory` on a wallet no longer sends a `blockchain.address.get_balance` request per address to backfill the running balances: it takes the current balance from the wallet's utxos, the satoshis of token coins included as before, so the numbers are the same. The standalone `getHistory({ addresses, provider, … })` requires the new `utxos`, the current utxos of `addresses` with the token coins, for the same; its `rawHistory` is marked `@internal`. A history load is bounded: its requests (the history per address when no `rawHistory` is given, the transactions and the headers fetched side by side, the spent outputs) keep at most 10 in flight together; the new `concurrency` option of the wallet `getHistory` and of the standalone function sets another bound, a positive integer or `Infinity`. A single-address wallet's `getHistory` now waits for its status watch and the fetch it triggered, as `getBalance` does.
- Reading a transaction with its input values (`getRawTransactionObject(hash, true)`) now fetches the spent transactions at most 10 at a time instead of all at once; a transaction with many inputs, such as a consolidation of the wallet's coins, put one request per input on the socket together. The result and the errors are unchanged.
- Single-address and watch-only wallets keep their cache (status, utxos, history) in memory only, as mainnet-js 3.1.7 did. next.14 wrote it to a `walletCache-…` record per wallet, the private key included, a second copy of the key the wallet's database row already holds, and one that a rollback to 3.1.7 would leave behind. Such a wallet now fetches its utxos and history once after it is constructed, as in 3.1.7. `pruneWalletCaches` and `deleteNamedWallet` find no record of theirs to remove, and `pruneWalletCaches` removes a record an earlier version wrote for one, as it does every record of a wallet not kept.
- Everything the library throws, and every promise it rejects, is now an `Error`. `getHistory` (and the wallets' `getHistory`) threw libauth's string for a transaction from the server that does not decode, and the transaction building behind `send` and the token operations threw a string for an input address that does not decode or tokens that do not add up; these are `Error`s with the same message. A caller with a `typeof error === "string"` branch for these can drop it and read `error.message`.
- New export `BroadcastRejectedError`, thrown by `sendRawTransaction`, and so by `submitTransaction`, `send`, `sendMax` and the token operations, when the server refuses the transaction. `reason` is the node's reject reason (e.g. `"txn-mempool-conflict"`, `"Missing inputs"`, `"dust"`, without BCHN's debug message), `txid` the refused transaction's id and `cause` the server's error. The message is still the server's text ("the transaction was rejected by network rules.\n\ntxn-mempool-conflict (code 18)\n"), so matching on it keeps working, but tell a refusal apart with `instanceof BroadcastRejectedError` and branch on `reason`. An answer that the node already holds the transaction (`"txn-already-known"`, `"txn-already-in-mempool"`, `"transaction already in block chain"`) is no refusal: an earlier broadcast of this very transaction went through (the node knows it by its txid, the hash of the bytes sent), so the broadcast returns the txid and a send its usual response; `alreadyKnown` on the error marks such an answer. A broadcast that times out or loses its connection is no refusal, as the transaction may have reached the node: see `BroadcastTimeoutError` below.
- A broadcast no longer waits without end for the server to report the transaction. `sendRawTransaction`, and so `submitTransaction`, every send and the token operations, used to subscribe to the transaction, broadcast it and wait for its first status with no timeout: a server that accepted the broadcast but never sent the status left the send pending forever. Once the server has accepted the broadcast, the wait is now 30 seconds; after it the server is asked once for the transaction (`blockchain.transaction.get`). When it has it, the txid is returned as before; when it does not, or the lookup fails, the new export `BroadcastTimeoutError` is thrown, with `txid`, the signed hex as `transaction` and the lookup's error as `cause`. The subscription is ended either way.
- A broadcast whose request times out (`ElectrumTimeoutError`) or loses its connection (electrum-cash's plain `Error("Connection lost")`) used to throw that error, with no txid: a caller could not tell whether the transaction went out, and a user who sent again got a new transaction, from other coins, so a payment that had gone through was paid twice. The server is now asked for the transaction in these cases too, after reconnecting: the txid is returned when it has it, and a `BroadcastTimeoutError` thrown when not, with the broadcast's error as `cause`. A `BroadcastTimeoutError` means the outcome is unknown: broadcast `error.transaction` again to settle it (the node takes it, or answers that it holds it, which returns the txid), never build a new spend. Every other error of a send means the transaction did not go out; a failure to connect before the broadcast also ends in a `BroadcastTimeoutError`, as the provider cannot tell it apart, which a rebroadcast settles all the same.
- A send, `sendMax`, the token operations and `submitTransaction` now return only once the wallet's own coins reflect the transaction: its spent coins gone from `getUtxos()` and its outputs to the wallet's watched addresses there, the HD change address among them, now counted as used. An HD wallet returned at once, and a single-address wallet on the first status of any kind (a block's, say) or after 2.5 s, so a second send right after the first could pick a spent coin and be refused with `BroadcastRejectedError` (`txn-mempool-conflict`). The wait starts once the server has reported the transaction and gives up after 10 s, after which the call returns as before; it never throws, the transaction having gone through. Callers that re-read the coins or waited between sends no longer need to.
- A token `send` with several mutable NFT requests whose commitments the wallet does not hold spends one mutable NFT per request, as it already did for requests matching an NFT exactly. Every such request after the first took the mutable NFT the first had picked, and the transaction then failed the token check ("…creates more mutable tokens than are available…") while the wallet held enough of them. A send with more such requests than the wallet has mutable NFTs of the category, and no minting NFT of the category in its pool to back the rest, now throws `InsufficientFundsError` ("No suitable token utxos available…") before anything is built. Minting NFT requests are unchanged: a minting NFT the send already spends backs any number of new minting NFTs, as consensus allows. A new mutable NFT is now backed the same way by a minting NFT of its category that the send spends, whatever the order of the requests, instead of consuming one of the wallet's mutable NFTs and destroying its commitment; a mutable NFT such a send spends anyway, for its fungible tokens or through `ensureUtxos`, comes back as change with its commitment.
- `HDWallet.fromId` restores an `hd:<network>:<xprv or tprv>:<depositIndex>:<changeIndex>` walletId, the form `toDbString` writes for a wallet made from an extended private key. It read the key as a mnemonic and threw "Invalid mnemonic, must be 12 or 24 words", as mainnet-js 3.1.7 does, so such a wallet could be serialized but not restored, and `replaceNamed` refused its id. The id formats are unchanged; mnemonic and xpub ids parse as before. mainnet-js 3.1.7 still cannot open such a row, so a wallet stored by its xprv cannot be rolled back to it: an app that rolls back keeps its HD wallets stored by mnemonic.
- An empty key no longer makes a wallet with a new random key: `fromWIF("")`, a `wif:<network>:` walletId (or one without its key part) and an `hd:<network>:` walletId without a key now throw an `Error` ("refusing to create wallet from empty WIF", "refusing to create wallet from a walletId without a key"), as an empty mnemonic already did. The other id forms with their value missing throw a clear `Error` instead of a `TypeError` or "Could not initialize wallet - insufficient parameters": `privkey:` ("refusing to create wallet from empty private key"), `seed:` ("refusing to create wallet from empty mnemonic"), `watch:` ("address is required to create a watch-only wallet") and `named:` ("Named wallets must have a non-empty name"). A caller that wants a random wallet calls `newRandom`.
- Every spend now draws its coins from one pool: the wallet's current coins, narrowed to `options.utxoIds` when given, minus the new `options.excludeUtxoIds` (`string[] | Utxo[]`, the forms `utxoIds` takes; ids the wallet does not hold are ignored, the txid matches in either case, and an id that is not a `txid:vout` outpoint, such as a bare txid, throws `InvalidRequestError` with `field` `"excludeUtxoIds"` and `value` the id as given, rather than leave the coin it meant spendable). `send`, `sendMax`, `getMaxAmountToSend`, `tokenGenesis`, `tokenMint` and `tokenBurn` honor it: an excluded coin is never an input, not as a BCH coin the selection picks, a token coin a fungible send needs, the input of an NFT request, a genesis input, a minting NFT or a burned token; `getMaxAmountToSend` reports the max over that pool. A coin listed twice in `utxoIds` is one coin of the pool, at the place of its first listing; before, `tokenBurn` counted its satoshis (and its tokens) twice in the token change it built. A caller that subtracted its reserved coins from `getUtxos()` to pass the rest as `utxoIds` can pass them as `excludeUtxoIds` instead. A coin in `options.ensureUtxos` must be in the pool: one that is excluded, outside the given `utxoIds` or not in the wallet now throws the new export `UtxoNotAvailableError` before anything is built, with `utxoId` (`txid:vout`) and `reason` (`"excluded"`, `"not-in-utxoIds"` or `"not-found"`). Before, `ensureUtxos` went into the transaction unchecked, so a caller who passed an `ensureUtxos` coin outside its `utxoIds` (or a coin the wallet no longer holds) now gets that error and has to add the coin to `utxoIds`. `tokenGenesis`, `tokenMint` and `tokenBurn` still pick their inputs themselves and do not spend `ensureUtxos`, but refuse a coin there outside the pool all the same. An `ensureUtxos` coin is compared by outpoint and spent as the wallet's own copy of it, so the satoshis and token data the caller's object carries no longer count.
- New send option `tokenUtxoIds` (ids or coins): the only token coins a spend may use. The pool's other token coins are left out, its BCH coins are not, so an identity operation can name the authhead (and the coins it means to spend) without reading the wallet's coins to build a `utxoIds` of every BCH coin. It narrows the pool of every spend (`send`, `sendMax`, `getMaxAmountToSend` and the token operations, whose own input choice included); ids the wallet does not hold are ignored, a malformed one throws `InvalidRequestError` (`field` `"tokenUtxoIds"`), and a token coin in `ensureUtxos` that it leaves out throws `UtxoNotAvailableError` with the new `reason` `"not-in-tokenUtxoIds"`. `excludeUtxoIds` still wins over it.
- New send option `excludeAddresses`: the addresses whose coins no input of the spend may use, on every spend (`send`, `sendMax`, `getMaxAmountToSend`, `tokenGenesis`, `tokenMint`, `tokenBurn`), e.g. an HD wallet's address the user has frozen. It is checked against the coins the wallet holds when the spend is built, so a coin that arrived since the caller looked is left out too, which a list of its outpoints in `excludeUtxoIds` cannot do. An address is compared by its locking bytecode, so its token-aware and plain forms are one. An entry that is not a cash address throws `InvalidRequestError` (`field` `"excludeAddresses"`), and a coin of an excluded address named in `ensureUtxos` throws `UtxoNotAvailableError` with `reason` `"excluded"`.
- `sendMax` and `getMaxAmountToSend` refuse a token coin in `options.ensureUtxos` with `InvalidRequestError` (`field` `"ensureUtxos"`, `value` the coin's `txid:vout`) before anything is built. The max counted only the BCH coins while `sendMax` spent the token coin as well: its tokens came back as change and the rest of its satoshis went to the miners, so a 50,000-satoshi token coin paid a fee of about 49,000 satoshis. A caller that wants a token coin's satoshis swept sends its tokens away first, or uses `send`. BCH coins in `ensureUtxos` are spent as before, as the first inputs.
- Every transaction `send`, `sendMax`, `tokenGenesis`, `tokenMint` and `tokenBurn` build is checked, before it is signed, for tokens its outputs destroy: per category the outputs must carry the inputs' fungible amount, and every NFT input must come back as it was or as the CashTokens rules let it change (a minting NFT as another minting NFT; a mutable one, when no minting NFT of its category is spent, with another commitment or as an immutable NFT). Only what a `tokenBurn` request names may go, one NFT per request that names one: a burn of one NFT whose transaction would spend and destroy an identical copy as well is refused. Otherwise the new export `TokenBurnError` is thrown, with `category`, `amount` (the fungible tokens missing, `0n` when an NFT is) and `nft` (the missing NFT's `capability` and `commitment`), and nothing is signed or broadcast. What a token operation may burn is internal to it: no send option allows a burn, so `send` and `sendMax` burn nothing. Before, only tokens created from nothing were refused, so a regression in the change burned tokens silently. `checkTokenQuantities: false` does not turn the check off: it turns off the token input matching and the token change of a send (its outputs are the requests as given), and the transaction it builds must still bring back every token its inputs carry. Only `tokenBurn`, for what its requests name, may destroy tokens. A hand-built mint off a minting NFT passes, as tokens created by a minting NFT or a genesis are no burn; one that drops a token coin it spends throws `TokenBurnError`, where it used to burn the token.
- A wallet without its private keys (a `watch:` wallet, a `WatchWallet`, an HD wallet from an xpub) refuses every spend with the new export `WatchOnlyError` before it reads or builds anything: `send`, `sendMax`, `tokenGenesis`, `tokenMint` and `tokenBurn`. A `WatchWallet` used to build and sign with a placeholder key and fail only at the broadcast, and the other two threw a plain `Error` ("Missing private key"). `getMaxAmountToSend` still answers for a watch-only wallet.

### Changed

- New `sweepTokenSatoshis` option of `sendMax` and `getMaxAmountToSend`: the max also spends each token coin of the pool whose satoshis above its dust limit pay for more than spending it and recreating its output, by the same fee estimate the max is priced with. The coin's tokens come back unchanged, holding their dust limit, on a change address of their own. A token coin on the usual 1000 sats is not worth it; one received with more is. A token coin in `ensureUtxos` is swept whether it pays or not, where a max send refuses it without the option. Off by default, as it puts token coins in a BCH send, linking them to its recipient; without it a max send leaves token coins out as before, those listed in `utxoIds` too.

- An HD wallet gives every change output of a transaction an unused change address of its own: the BCH change one, and each token change output (a category's fungible change, an NFT that comes back, the minting NFT a mint re-creates, a burn's remainder) the next ones in turn. All change went to the one current change address, so a coin later sent on from it showed every other coin of that transaction there: the change of every token category the send touched, and the BCH change. A single-address wallet is unchanged, as it has one address. The protected `getTokenChangeAddress` is gone; `getChangeAddresses(count)` and `planChangeAddresses()` hand out the addresses.

- `new IndexedDBProvider(dbName)` requires `dbName`. Without it the provider opened a database named `"wallet"`, which no wallet stores to: `named()` and `getNamedWalletId` use `"bitcoincash"` and `"bchtest"`. A caller that relied on the default passes `"wallet"`.
- `WalletCacheI`'s `init`, `flush`, `getByPath` and `setStatusAndUtxos` are marked `@internal`: the wallets call them, and a caller who does can break the wallet's own state. `get`, `getByIndex` and `persist` stay.
- `SignedMessage.sign(message, privateKey)` returns `{ signature }` only and no longer computes a DER or Schnorr signature; `SignedMessage.verify(message, signature, address)` takes the address as a required argument and returns `{ valid }` only. Only the static methods remain; `new SignedMessage()` has no methods.
- `getNetworkProvider` and `setGlobalProvider` take and return `ElectrumNetworkProvider` instead of the removed interface; nothing changes for a caller that passed one.
- `ElectrumNetworkProvider.getRawTransaction(hash)` takes only the hash and returns the hex. The `verbose` and `loadInputValues` overloads are gone: `getRawTransaction(hash, true)` becomes `getRawTransactionObject(hash)`, and `getRawTransaction(hash, true, true)` becomes `getRawTransactionObject(hash, true)`. Both read and write the same `txraw-` and `tx-` cache entries as before.
- On `ElectrumNetworkProvider`, the plumbing is no longer public: `transport` is private, `performRequest` and `subscribeRequest` are protected (for a subclass), and `subscribeToHeaders` is private; use `watchBlocks(callback, false)` for every header including the current one. `subscriptions` is a read-only getter marked `@internal`, and `mine` is marked `@internal` (regtest only).
- `tokenMint(requests, options)`: the `deductTokenAmount` parameter is gone, and with it the burn of one fungible token per mint off the minting NFT; the minting NFT always comes back with all its fungible tokens. Drop the second argument: `tokenMint(requests, false, options)` becomes `tokenMint(requests, options)`. A caller that wants fungible tokens burned burns them with `tokenBurn`.
- `getMaxAmountToSend(options)`: the options are the argument itself, no longer wrapped in `{ options }`, and the `outputCount` parameter is gone; the max is always that of a `sendMax`, to one output. `getMaxAmountToSend({ options: spendConfig() })` becomes `getMaxAmountToSend(spendConfig())`. A caller that split the max over several outputs subtracts the size of the extra outputs itself.
- New export `namedWalletExists(name, dbName?)`, shaped like `getNamedWalletId`: whether the database (the mainnet one, `"bitcoincash"`, by default) holds a wallet of that name. It constructs no wallet and opens no subscription, closes the database even when the read throws, and throws on an empty name or without a `StorageProvider`. A Cashonize-style raw IndexedDB check (`namedWalletExistsInDb`) can call it.
- `named`, `replaceNamed` and `newRandom` lose their `dbName` parameter, and `named` its `force`: the database is always the one of the class's network (`bitcoincash`, `bchtest`, `bchreg`), which is what Cashonize passes by default. Drop the extra arguments; to refuse an existing name, check `namedWalletExists(name, dbName)` first. A `named:<network>:<name>:<database>` walletId still loads when its database part is the network's one, and throws for any other database instead of reading a database `named` no longer opens. `getNamedWalletId` and `deleteNamedWallet` keep their `dbName`.
- Made internal (`protected`, or `private` where only the class uses it), so a caller can no longer read or call them: `walletType` (tell the kind of wallet with `instanceof HDWallet`, or by the prefix of `toDbString()`), `watchStatus` (the HD form takes `{ debounce }` only, no longer a bare number), `waitForUpdate` (the HD form takes `indices: { [branch]: index }` only, its `depositIndex` / `changeIndex` aliases are merged into it), `watchTransactionHashes`, `watchTransactions`, the HD wallet's `xPriv`, `xPrivNode`, `xPubNode`, `walletId` (its cache record id), `utxos`, `statuses`, `watchCancels`, `watchPromise` and `branches`, and the watch-only wallet's `watchPromise` and `updatePromise`. `mnemonic`, `derivation`, `xPub`, `indices`, `rawHistory` and `walletCache` stay public.
- The wallet factories take a last `options` parameter, `WalletFactoryOptions` (new export), whose `provider` the wallet uses from the start: `Wallet` / `TestNetWallet` `fromId(walletId, options?)`, `fromWIF(wif, options?)` and `newRandom(name?, options?)`, `HDWallet` / `TestNetHDWallet` `fromId(walletId, options?)` and `newRandom(name?, options?)`, and `named(name, options?)` / `replaceNamed(name, walletId, options?)` on every wallet class. The first status subscription, an HD wallet's address discovery and every later request go to that provider, and the network's global provider is neither created nor used, so a caller no longer has to set `DefaultProvider.servers` before the first wallet to keep its addresses off a default server. A provider of another network rejects as `setProvider` does ("a mainnet provider cannot serve a regtest wallet"). Without the option nothing changes: the factory takes the global provider when it makes the wallet. A wallet made with `new` and no factory now takes the global provider when `wallet.provider` is first read, instead of in the constructor.
- A `utxoIds` coin the wallet does not hold, such as one spent between the caller's read and the spend, now throws `UtxoNotAvailableError` with `reason` `"not-found"` and `utxoId` the coin's `txid:vout` (the first such coin), as the same coin in `ensureUtxos` does, instead of a plain `Error` ("Utxos [...] not found in wallet"). `send`, `sendMax`, `getMaxAmountToSend`, `tokenGenesis`, `tokenMint` and `tokenBurn` throw it. A caller that matched the message checks `instanceof UtxoNotAvailableError` instead.
- With `Config.UseIndexedDBCache`, a failed read or write of the electrum cache rejects with the IndexedDB `DOMException` (an `Error`, e.g. a `QuotaExceededError`), or an `Error` when IndexedDB gives none, instead of the raw `Event`. The batched cache reads and writes behind history and raw transactions no longer wait forever when IndexedDB aborts their transaction: they reject with its error. Nothing changes for a caller that only logs the error; one that read the `Event`'s `target.error` reads the error itself.
- A WIF the wallet refuses (`fromWIF`, `fromId("wif:…")`) throws the new export `InvalidWifError` instead of a plain `Error`, with `reason` `"malformed"` (not a WIF), `"uncompressed"` or `"network"` (a WIF of the other network), and `network` the WIF's own network (`NetworkType.Mainnet` or `NetworkType.Testnet`) when it could be read; the messages are unchanged and never contain the WIF. New export `decodeWif(wif)`, returning `{ network, compressed, privateKey }` for any well-formed WIF without judging it, and throwing `InvalidWifError` (`"malformed"`) otherwise: a caller that guessed a WIF's network or form from its first character (Cashonize's sweep QR filter) reads them from it instead. A testnet WIF is also chipnet's and regtest's.
- A walletId that cannot be read throws the new export `InvalidWalletIdError` instead of a plain `Error`, from `fromId`, `replaceNamed` and `named` (with a stored id), and from `deleteNamedWallet` for a row whose id cannot be read: `reason` `"network"` (the network part missing or another network's, or for `saveNamedWallet` not the database's), `"kind"` (an unknown type part, or one the class does not load, such as an `hd:` id given to `Wallet.fromId`), `"missing-value"` (no key, address or name) or `"database"` (a `named:` id naming another database than the network's), and `kind` the id's type part (`"wif"`, `"seed"`, `"hd"`, `"watch"`, `"privkey"`, `"named"`) when it is one, never another part of the id. The messages are unchanged. What the id's value holds is still judged by its own checks: a WIF throws `InvalidWifError`, a mnemonic or an extended key a plain `Error`.
- A rate source that answers something other than a positive finite number (`NaN`, `0`, a negative number, a missing field) counts as a failed fetch: `ExchangeRate.getQuote` and the conversions throw an `Error` (or, with `staleOnError`, return the last known rate as `stale: true`), and the answer is never cached. Before, such a rate was returned as fresh and cached for its TTL, so a conversion gave `NaN` or divided by zero. A cached `rate-<symbol>` entry holding such a rate is ignored and fetched again.
- A single-address or watch-only wallet's `getHistory` reads its transactions from the wallet's own history, the same update its utxos and so the running balances come from, instead of fetching the address's history from the server again; a transaction the server knew of but the wallet had not processed yet could show up with a balance that did not count it. The history matches `getRawHistory()`, and the next address notification brings it up to date. Nothing changes for a caller.
- `tokenBurn`'s fungible change holds the standard 1000 sats of a token output, as a send's fungible change does, and the rest of the spent coins' satoshis go to the BCH change. Before, the change took the satoshis of every coin of the category the burn matched, spent or not, out of the BCH change, so a burn from several token coins pulled in more BCH than it needed or failed for want of it; and a burn that used up the tokens of the coins it spent, leaving others of the category, sent all those satoshis to a plain output of their own. Nothing to change for a caller.
- A burn request with neither a positive fungible amount nor an NFT now throws `InvalidRequestError` (`field` `"nft"`), from the `TokenBurnRequest` constructor and from `tokenBurn` for a plain object, before any coin is read. Before, such a burn spent a coin of the category and returned it whole, a transaction that burned nothing and paid a fee. A caller that can build one, e.g. from an amount the user typed as 0, checks for it first.
- `tokenBurn` burns exactly what its requests name, and its token check allows no more: the fungible amount a request names, and the NFT of a request that destroys one, never an NFT the burn brings back. A request with an NFT and no amount destroys that NFT also when its coin carries fungible tokens, which come back on their own in a 1000 sat token output; before, that burn sent the NFT back with its tokens and burned nothing. A request with an amount burns it from the matching coins (the fungible-only coins of the category, or with an NFT given, the coins carrying that NFT), and every NFT on a spent coin comes back as it was, on that coin's satoshis; before, one NFT came back for all of them, so a burn of 40 tokens over two coins with the same minting NFT destroyed one minting NFT, which the check let through, and the change counted the tokens of matching coins the burn did not spend. Asking more than the matching coins carry now throws `InsufficientFundsError` (`asset: "token"`, `category`); before, the burn took all they had, and a fungible burn off an NFT whose coin carried none destroyed the NFT. A caller that asked for more than it holds to burn all of it passes the amount it holds.
- Several `tokenBurn` requests for the same NFT or category each spend their own coins, a coin one request spends being left out for the next. Before, every request picked from all the matching coins: two requests for an NFT the wallet holds twice spent and destroyed one copy, and two fungible burns of one category built their change from the same coin and were refused by libauth for creating tokens.
- A token output whose request names no `value` (a token `send`, a `tokenGenesis` request, token change) holds its dust limit where that is above the standard 1000 sats. The limit grows with the token data, and an NFT whose commitment is longer than about 110 bytes needs more than 1000 (up to about 1060 at 128 bytes, depending on its fungible amount and the locking bytecode): such an output was built at 1000 sats, so `broadcast: false` returned a transaction the network refuses, and a broadcast was refused as `"dust"`. A `value` the request names is still used as given. Nothing to change for a caller.
- `sendMax` refuses with `InsufficientFundsError` (`asset: "bch"`, `data` with `required`, the fee plus the dust limit, and `available`) when the max is below the dust limit of the destination's locking bytecode (546 sats for P2PKH, 576 for P2SH32), before anything is built. Before, it built the output anyway: `broadcast: false` returned a transaction the network refuses, and a broadcast was refused as `"dust"` with `BroadcastRejectedError`. `getMaxAmountToSend` still returns the max; a caller that offers a max send compares it with the dust limit, or catches the error.
- New export `saveNamedWallet(name, walletId, dbName?)`: stores a wallet id under a name, replacing the id stored under that name if there is one, the same row `replaceNamed` writes, without constructing the wallet, so no provider is created and no subscription opened (`replaceNamed` constructs the wallet, and an HD wallet starts its discovery). `dbName` is the database of the id's network by default; another network's database (`"bitcoincash"`, `"bchtest"`, `"bchreg"`) is refused, other names take any id. The id's form is checked as `deleteNamedWallet` reads it, and one it could not read throws `InvalidWalletIdError`; its key is not checked, so store ids that `toDbString()` returned. Cashonize's `(await TestNetWallet.replaceNamed(name, walletId)).stop()` for the chipnet copy of a new wallet becomes `saveNamedWallet(name, walletId, "bchtest")`, and an import's two copies the same.
- `getNamedWalletId(name, dbName?)` returns `undefined` for a row that holds an empty id, as for a missing name, instead of `''`. A caller that checked the result for `undefined` before loading no longer goes on to `fromId('')`.
- A watch-only HD wallet (`hd:<network>:<xpub>`) keeps its cache in memory only, like the single-address wallets: it reads no `walletCache-…` record and writes none. mainnet-js 3.1.7 never wrote one for it (its write threw on the missing private keys), while the library wrote one, a record a rollback to 3.1.7 would leave behind. Such a wallet fetches its addresses' utxos and history again after it is constructed, as in 3.1.7. Nothing changes for a caller.
- An HD wallet on a node deeper than an account derives `branch/index` below that node again, deposit and change, as mainnet-js 3.1.7 did: a mnemonic id with a depth-4 path such as `hd:<network>:<mnemonic>:m/44'/0'/0'/0`, and the xpub or xprv of such a node. next.14 made it a single chain at the bare index (no change branch), so a wallet 3.1.7 had stored that way showed other addresses, and not its coins. A depth-5 (address-level) node opens again, deriving below it as 3.1.7 did, instead of throwing "too deep". A caller that used a depth-4 node to reach one chain of an account opens the account node and reads that branch. Cashonize stores account-level paths only, which are unchanged.
- A token `send` with a new mutable NFT request and no mutable NFT of the category left to claim spends a minting NFT of the category to back it, which comes back as change with its commitment, fungible tokens and satoshis. Before, only a minting NFT the send spent anyway backed one, so the send threw `InsufficientFundsError` ("No suitable token utxos available…") while the wallet held the minting NFT: a wallet whose only token coin is the baton could not send a new mutable NFT. The mutable NFTs the send claimed for its other mutable requests come back as change as they were, since a spent minting NFT backs every new mutable NFT: three such requests from a wallet with two mutable NFTs and the baton mint three new ones and keep the two, where they threw before. A caller that sent the baton back to itself in the same request list, to get it spent, can drop that request.
- `options.utxoIds` and `options.ensureUtxos` match a coin's txid in either case, as `excludeUtxoIds` already did, on every spend (`send`, `sendMax`, `getMaxAmountToSend`, `tokenGenesis`, `tokenMint`, `tokenBurn`): a txid is hex, so an uppercase one names the same coin, and a coin listed in both cases is one coin of the pool. Before, an uppercase txid there threw `UtxoNotAvailableError` with `reason` `"not-found"` for a coin the wallet holds. The `utxoId` of a `UtxoNotAvailableError` now carries the txid lowercased. A caller that lowercased its ids first can drop that.
- The category of a `TokenSendRequest`, `TokenMintRequest` or `TokenBurnRequest` is lowercased by its constructor, and `tokenMint` and `tokenBurn` lowercase it on a plain request object too, working on a copy and leaving the caller's object as it was; `send` already made a `TokenSendRequest` of every plain token request. A category in uppercase now finds the wallet's coins of that category, and `SendResponse.categories` lists it lowercased. Before, it was kept as given, so a `send` of it threw `InsufficientFundsError` ("No suitable token utxos available…" or "Not enough token amount to send"), and `tokenMint` and `tokenBurn` threw that they found no coins of the category, while the wallet held them. A caller that reads `request.category` back gets the lowercase form.
- The NFT commitment of a `TokenSendRequest` or `TokenBurnRequest` is lowercased by its constructor (on a copy of the `nft` object, the caller's left as it was), so a commitment in uppercase names the wallet's NFT with those bytes; `send` and `tokenBurn` build such a request from a plain object too. Before, the commitment was compared as given: sending or burning an NFT by an uppercase commitment threw `InsufficientFundsError` while the wallet held it, and a mutable NFT request with one did not match its own coin and so was taken for a new commitment: depending on the coins' order, it spent another mutable NFT of the category and overwrote that one's commitment. A caller that reads `request.nft` back gets the copy, with the lowercase commitment.
- A token `send` puts the coins it picks for mutable NFT requests after those of the other NFT requests in its inputs, whatever the order of the requests: first the caller's `ensureUtxos`, then the coins of the other NFT requests in request order, then those of the mutable NFT requests (a minting NFT spent to back one included), then the fungible token coins the amounts need, then BCH coins. Before, the NFT coins followed the order of the requests. A caller that relies on a coin's input position pins it with `ensureUtxos`, which still go first.

### Removed

- The `encrypted-storage` entry, with `EncryptedStorageProvider`, `wrapProvider`, `changePassphrase`, `encryptPlaintextRows`, `removeEncryption` and `DecryptionError`. Wallet ids are stored as plaintext rows, as mainnet-js 3.1.7 stores them. A caller that wrapped a provider sets `BaseWallet.StorageProvider` to the provider itself; the library no longer reads `enc:v1:` rows, so one that wrote them runs `removeEncryption` with an earlier build first.
- `StorageProvider.getInfo()` and `IndexedDBProvider.getInfo()`, which returned the constant `"indexedDB"`. A custom `StorageProvider` drops its implementation; a caller that read it knows which provider it set.
- `IndexedDBProvider`'s second constructor parameter, `storeName`: the rows are always in the `"wallet"` store, where mainnet-js 3.1.7 keeps them. A caller that passed `"wallet"` drops the argument; one that passed another store moves its rows to `"wallet"`.
- `WalletDbEntryI.id`: a row is `{ name, wallet }`, and no provider ever set an `id`. A caller that read `row.id` uses `row.name`, the row's key.
- `Config.UseLocalStorageCache` and the localStorage cache behind it. localStorage holds about 5 MB per origin and is shared with the host app, so it never suited raw transactions or wallet cache records; a caller that set it sets `Config.UseIndexedDBCache` instead, or leaves it unset: then raw transactions and headers are not cached, and each HD wallet keeps its address cache in memory. What an earlier build or mainnet-js wrote to localStorage under `bch-wallet-lib:`-prefixed or bare `txraw-…`, `tx-…`, `header-…` and `walletCache-…` keys is neither read nor removed; remove it yourself, as `walletCache-…` entries hold private keys.
- `Config.UseMemoryCache` and the process-wide memory cache behind it. Without a cache flag the raw transactions and headers are not cached, and each HD wallet keeps its address cache in memory for its own life, as before; a caller that set it for a cache shared by every provider and wallet in the process sets `Config.UseIndexedDBCache` instead (in Node over an IndexedDB implementation such as fake-indexeddb), or drops it.
- `clear()` of the caches, reachable as `provider.cache.clear()`. It emptied the whole IndexedDB cache store and nothing called it; a caller that wants the cache gone deletes the `ElectrumNetworkProviderCache` database itself, which the library recreates when it next opens it.
- `Config.DefaultIpfsGateway` and `Config.setIpfsGateway`: nothing in the library fetches from IPFS, so the setting had no effect. A caller that resolves IPFS links keeps its gateway in its own settings.
- The main-entry export `StorageProvider`. `BaseWallet.StorageProvider` still takes a provider class such as `IndexedDBProvider`; a caller that typed its own provider with `StorageProvider` types it with `NonNullable<typeof BaseWallet.StorageProvider>`, or implements the methods `IndexedDBProvider` has.
- `ElectrumNetworkProvider.cache` is private. The cache is chosen by `Config.UseIndexedDBCache`, as before; a caller that read or wrote entries through it reads the transactions and headers through the provider's methods.
- The `libauth` namespace export (`decodeTransaction`, `encodeTransaction`, `generateTransaction`, `hexToBin`, the P2PKH wallet templates and their compiler helpers) and the `binToHex` / `hexToBin` re-exports: import them from `@bitauth/libauth`, which also has `hashTransaction` for a transaction's id.
- `atob` and `btoa`: use the platform's, or libauth's `binToBase64` / `base64ToBin`.
- `getWeakRandomInt`, `sanitizeAddress` and `derivedNetwork`, with no replacement.
- `isValidAddress`, `deriveTokenaddr` and `convertAddress`: use libauth's `decodeCashAddress` and `encodeCashAddress`.
- `toBch`, `toSat`, `toCurrency` and `convertObject`: use `convert(value, from, to)`, e.g. `convert(Number(sats), "sat", "usd")` for `toCurrency(sats, "usd")`.
- `getAddrsByXpubKeyObject`: call `getAddrsByXpubKey(xpub, path, count)`.
- `getXpubKeyInfo` and `getXpubKeyInfoObject`: use libauth's `decodeHdPublicKey`.
- `deriveHdPaths`, `getXPubKeys`, the `XPubKey` class and the `DERIVATION_PATHS` constant: derive the seed with libauth's `deriveSeedFromBip39Mnemonic(mnemonic)` and call `getXPubKey(seed, path, network)` per path. `getXPubKey` does not refuse the root path `m` as `deriveHdPaths` did.
- `SignedMessage.verify`'s `publicKey` parameter, with the DER, Schnorr and compact verification it enabled: only a recoverable signature verifies, against the address that signed it. The `raw` and `details` fields of the sign and verify responses go with it, as do the types `SignedMessageRawI`, `SignedMessageDetailsI`, `VerifyMessageDetailsI` and `SignedMessageI`.
- The `Network` object and type: use `NetworkType` (`Network.MAINNET` is `NetworkType.Mainnet`); the enum's values are the same strings.
- From the entry, still used inside the library: `amountInSatoshi`, `sanitizeUnit`, `UnitEnum`, `checkUtxos`, `delay`, `deriveCashaddr`, `toCashaddr`, `toTokenaddr`, `isTokenaddr`, `checkTokenaddr`, `derivePublicNodeCashaddr`, `getRuntimePlatform`, `RuntimePlatform`, `hash160`, `sumUtxoValue`, `sumTokenAmounts`, and the type `UtxoId`; `derivePublicKeyHash` and the type `PrivateKeyI` are gone altogether, and `isTokenaddr` is private to the library. The interface module is no longer re-exported whole: the entry exports `NFTCapability` and the types `Utxo`, `TokenI`, `TxI`, `HexHeaderI` and `HeaderI`.
- The `NetworkProvider` interface, which only `ElectrumNetworkProvider` implemented. Type a provider as `ElectrumNetworkProvider` instead (Cashonize: `test/bchWalletLib.test.ts`).
- `ElectrumNetworkProvider.getHeader(height, verbose)`. Use `(await provider.getHeaders([height])).get(height)`, the decoded header; the hex form has no replacement. The `header-<network>-<height>-false` cache entries of mainnet-js are left in place and no longer read or written; the decoded headers keep their `…-true` entries.
- `ElectrumNetworkProvider.ready()`, which only called `connect()`. Call `connect()` instead; the provider still connects on its first request by itself.
- The `unit`, `start`, `fromHeight` and `toHeight` options of `getHistory`, `WatchWallet.getHistory` and `HDWallet.getHistory`. History values are always satoshis: convert them with `convert` or `ExchangeRate.getQuote`. Page with `count` (the newest `count` items) and filter by `blockHeight` on the result. `count` and `concurrency` stay.
- `ElectrumNetworkProvider.getBalance`, and the `ElectrumBalanceI` type. Sum `provider.getUtxos(address)` with their satoshis instead, which counts the token coins as `blockchain.address.get_balance` did.
- The `toHeight` parameter of `ElectrumNetworkProvider.getHistory(cashaddr, fromHeight?)`, and of `getRawHistory(fromHeight?)` on the wallets, with the `branches` option of `HDWallet.getRawHistory`. The history always runs to the tip, mempool included.
- `ExchangeRate.get(symbol, useCache)`, replaced by `ExchangeRate.getQuote(symbol, { staleOnError })`: `await ExchangeRate.get(c)` becomes `(await ExchangeRate.getQuote(c)).rate` (Cashonize: `store.ts`, `ExchangeRate.get(currency, true)`). `useCache` has no replacement: a rate is always cached for its TTL, and a fresh one is fetched after it.
- The rest of the exchange-rate surface: `ExchangeRate.getRateFromLocalStorage`, `getRateFromGlobalScope` and `cacheRateInGlobalScope`; the `ExchangeRate` instance (its constructor and `symbol`, `rate`, `ttl` and `toString`, which returned nothing); `getExchangeRatePromise`, `getRateFromExchange`, `getTtl`, `getUsdRate` and `Config.DefaultCurrency`, which only `getExchangeRatePromise` read. Use `ExchangeRate.getQuote`. The `rate-<symbol>` localStorage entries keep their key and format.
- From the entry: `getGlobalProvider`, still used inside the library, and `initProvider`, `initProviders` and `disconnectProviders`, now the library's test setup and left out of the build, with their `USE_MOCK_PROVIDER` switch to a mock chain. Build a provider with `createProvider(network, servers, { connectTimeout, requestTimeout })`, register it with `setGlobalProvider` and close it with its own `disconnect()`. The regtest `mine` export is gone too; `provider.mine` remains, marked `@internal`. An app's tests that want an in-memory chain build one from `@paryonusd/mem-cash` as `scripts/check-dist-errors.mjs` does: `new ElectrumNetworkProvider(asTransport(createIndexer({ addressPrefix: "bchreg" })), NetworkType.Regtest)`.
- The `buildUnsigned` send option, the `unsignedTransaction` and `sourceOutputs` fields of a response, and `Wallet.signUnsignedTransaction`. Every send now signs. A caller that needs a transaction it does not broadcast passes `broadcast: false` and gets the signed hex in `transaction`; one that signs dApp-built transactions signs them with libauth, as Cashonize already does, since `signUnsignedTransaction` overwrote every input with the wallet key's P2PKH unlock.
- The `feePaidBy` send option and the `FeePaidByEnum` export. The fee always comes out of the BCH change, as it did by default; a caller that wanted an output to pay it lowers that output's value by the fee itself, e.g. by sending `getMaxAmountToSend` with `sendMax`. A send with no output at all now throws "A send needs at least one output" rather than "Attempted to specify feePaidBy on zero length SendRequest".
- The `coin-control` entry, with every selection, ordering and fee strategy and their types, and the send options that took them: `coinSelection`, `inputOrdering`, `outputOrdering` and `fee`. A send selects its coins in the pool's order (narrow or order the pool with `utxoIds` and `excludeUtxoIds`, pin coins with `ensureUtxos`), puts the requested outputs first, then the token change, then the BCH change, and pays the relay fee rate (`Config.RelayFeePerByte` when set, otherwise the server's checked rate, never below 1 sat/byte). Nothing to change for a caller that passed none of them. A send no longer asks the server for the block height, which only the selection hooks were given.
- The `slpSemiAware` send option and `slpSemiAware()` (with the `_slpSemiAware` field): `getUtxos` and the spends no longer leave out coins of 546 sats or less. Such a coin is spent like any other; a caller that must keep it narrows the spend with `excludeUtxoIds`. Before, the option also switched the filter on for the wallet for good, and `getBalance` never applied it.
- The `branches` option of `HDWallet.getUtxos` and `HDWallet.getBalance`: both always cover every tracked branch. A caller that wants one branch's coins filters the returned utxos by address (`getAddressByBranch`).
- The `changeAddress` send option: the BCH change always goes to the wallet's `getChangeAddress()`, as the token change already did. A caller that wants the change elsewhere sends it on in a second transaction.
- The `queryBalance` send option and `SendResponse.balance`: a send no longer reads the balance after broadcasting. Call `getBalance()` after the send resolves; the send waits for the wallet to see its transaction, so the balance includes it.
- `SendResponse.explorerUrl` and `BaseWallet.explorerUrl()`. Build the link from `txId` with the explorer of your choice.
- The `awaitTransactionPropagation` send option, the `awaitPropagation` parameter of `submitTransaction` (now `submitTransaction(transaction)`) and that of `ElectrumNetworkProvider.sendRawTransaction` (now `sendRawTransaction(txHex)`). A broadcast always waits until the server reports the transaction, and a refusal always rejects with `BroadcastRejectedError`. Before, `false` returned the txid at once and swallowed a refusal, so a transaction the server refused looked sent. Drop the argument; a caller that passed `false` awaits the call instead.
- `TokenBurnRequest.cashaddr` is gone: the token and BCH change of a burn always go to the wallet's change addresses. Drop the field; a caller that sent the change elsewhere sends it on in a separate transaction.
- The tuple form of send requests (`SendRequestArray`): `[cashaddr, value]`, `["OP_RETURN", data]` and `["OP_RETURNB64", base64]` in a request array. `SendRequestType` keeps the object forms. Write `{ cashaddr, value }` and `OpReturnData.fromArray([data])` instead. The number form `[cashaddr, 1000]` threw a `TypeError` ("Cannot convert undefined to a BigInt").
- `OpReturnData.parse(hex)` and `OpReturnData.from(data)`. `from(data)` becomes `fromArray([data])`; `parse(hex)` becomes `OpReturnData.parseBinary(hexToBin(hex)).map(binToUtf8)` (libauth), and keeping the chunks as bytes is usually what a reader of on-chain data wants. `OpReturnData.fromUint8Array` is no longer public either: build data with `fromArray`, or `new OpReturnData(script)` for a complete OP_RETURN script.
- `Wallet.encodeTransaction` and `HDWallet.encodeTransaction` are protected, as `BaseWallet.encodeTransaction` already was. They took a raw private key as a parameter. To build a signed transaction without broadcasting it, call `send(requests, { broadcast: false })` and read `transaction`; `submitTransaction(hexToBin(transaction))` broadcasts it later.
- The model helpers leave the main entry, which now lists its models instead of re-exporting `wallet/model.ts` whole: `fromUtxoId`, `toUtxoId`, `asSendRequestObject`, `checkTokenCategory`, `checkTokenCommitment`, `toTokenAmount`, `checkTokenOutput`, `checkGenesisRequest`, `checkMintRequest`, `checkBurnRequest`, `SourceOutput` and the `WalletTypeEnum` enum. `SendRequest` and `SendResponse` are exported as types only: pass `{ cashaddr, value }` objects where `new SendRequest(…)` was written. The request classes `TokenSendRequest`, `TokenGenesisRequest`, `TokenMintRequest`, `TokenBurnRequest` and `OpReturnData` stay. A caller of `toUtxoId` writes `` `${txid}:${vout}` ``; the request checks run in the request constructors and the token operations.
- `createWallet`, `createWalletResponse`, `walletFromId`, `namedWallet`, `namedWalletExists(body)`, `replaceNamedWallet(body)` and `walletClassMap` (the whole of `wallet/createWallet.ts`). Construct a wallet with its class instead: `Wallet.fromId(id)` / `HDWallet.fromId(id)` (and the `TestNet` classes) for a stored id, `named(name)` / `replaceNamed(name, walletId)` for a named one, `newRandom()` for a new one.
- `decodeTransaction`. Read a transaction with `provider.getRawTransactionObject(txid, loadInputValues)` instead (e.g. `wallet.provider.getRawTransactionObject(txid, true)`), which returns the server's verbose transaction; to decode a transaction you hold as hex, use libauth's `decodeTransaction`. `getTransactionHash` is still exported.
- `getInfo()` on every wallet class, the `toString()` overrides of `BaseWallet`, `Wallet` and `HDWallet`, `Wallet.getSeed()` and `BaseWallet.isTestnet`. An unnamed wallet's `toString()` returned its walletId with the mnemonic, WIF or private key in it, so a wallet that reached a log or a template printed its keys; `String(wallet)` is now `[object Object]`. Read the fields instead (`mnemonic`, `derivationPath`, `privateKeyWif`, `cashaddr`, `network`, ...), `toDbString()` for the id to store, and `wallet.network !== NetworkType.Mainnet` for `isTestnet`.
- The types `WalletRequestI`, `WalletResponseI`, `WalletInfoI`, `MnemonicI` and `WalletI` (`BaseWallet` no longer `implements WalletI`).
- The waits and the watches no caller used: `waitForBalance`, `watchTokenBalance`, `waitForTokenBalance`, `getLastTransaction`, `waitForTransaction` (with the types `WaitForTransactionOptions` and `WaitForTransactionResponse`), `waitForBlock` on the wallet and on `ElectrumNetworkProvider` (and its `NetworkProvider` declaration), and `watchDoubleSpends` with `ElectrumNetworkProvider.subscribeToDsproof` and the `DsproofData` type. Wait on `watchBalance(cb)` or `watchBlocks(cb)` instead, or poll `getBalance()` / `getUtxos()`; a transaction is read with `provider.getRawTransactionObject(txid)`.
- The token balance wrappers `getTokenUtxos`, `getTokenBalance`, `getNftTokenBalance`, `getAllTokenBalances` and `getAllNftTokenBalances`. Each read `getUtxos()` again; filter one `getUtxos()` snapshot instead, e.g. `utxos.filter((u) => u.token?.category === category)` for the coins and the sum of their `token.amount` for the fungible balance.
- `BaseWallet.namedExists` (static, and the protected method it called), which constructed a wallet to look the name up. Use the new free function `namedWalletExists(name, dbName?)`.
- `HDWallet.fromSeed(mnemonic, path?, depositIndex?, changeIndex?)`, `HDWallet.fromXPub(xpub)` and `HDWallet.fromXPriv(xprv)`, merged into `HDWallet.fromId`: use `fromId("hd:<network>:<mnemonic>:<path>:<depositIndex>:<changeIndex>")` (the path and indices may be left out, e.g. ``fromId(`hd:mainnet:${mnemonic}`)``), `fromId("hd:<network>:<xprv>")` and `fromId("hd:<network>:<xpub>")`, the forms `toDbString()` writes. `HDWallet.scanMoreAddresses`, the `HDWalletEvents` type, and `getChangeTokenAddress`: the token change address is internal (see Changed).
- `Wallet.fromSeed(mnemonic, path?)` and `Wallet.fromPrivateKey(key)` (static), merged into `fromId("seed:<network>:<mnemonic>[:<path>]")` and `fromId("privkey:<network>:<hex key>")`, or `fromWIF(wif)` for a key you hold; the stored `seed:` and `privkey:` ids load as before. The classes `WifWallet`, `TestNetWifWallet` and `RegTestWifWallet`, merged into `Wallet` / `TestNetWallet` / `RegTestWallet`: their `fromWIF` and `fromId("wif:…")` give the same wallet. A random WIF wallet (`WifWallet.newRandom()`) can no longer be made; `newRandom()` makes a seed wallet. `Wallet.parentDerivationPath` and `Wallet.parentXPubKey`, which a seed wallet derived at construction and nothing read, and `TestNetWallet.faucetServer`.
- The static watch-only constructors `watchOnly(address)`, `fromCashaddr`, `fromTokenaddr` and `fromPublicKey`: make a watch-only wallet with `fromId("watch:<network>:<address>")` on `Wallet` / `TestNetWallet`, the form a stored watch-only wallet has. The uncompressed `publicKey` field, and `getPublicKeyHash()`, `getPublicKey()` and `getPublicKeyCompressed()`: read the fields `publicKeyHash` and `publicKeyCompressed` (both `Uint8Array`, `binToHex` them for hex); derive an uncompressed key with libauth's `secp256k1.uncompressPublicKey(publicKeyCompressed)` if you need one.
- From the entry: `RegTestWallet`, `RegTestHDWallet`, `WatchWallet`, `TestNetWatchWallet`, `RegTestWatchWallet` and `WalletTypeEnum`; `export * from "./wallet/interface.js"` became the explicit types `CancelFn` and `SendRequestOptionsI`. The regtest classes are test infrastructure; a watch-only wallet is `Wallet.fromId("watch:<network>:<address>")`, and its type is told by `toDbString()`'s prefix or `instanceof HDWallet`.
- The static `networkPrefix` and `walletType` fields of the wallet classes, which only the removed static constructors read. Read the instance `networkPrefix` or `network` of a wallet instead.
